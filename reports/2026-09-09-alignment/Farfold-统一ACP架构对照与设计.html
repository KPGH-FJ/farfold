如果 Farfold 统一使用 ACP，会改变什么？

工作台继续由 Farfold 自己做；与 Agent 通信改为共用一套 ACP 客户端。
Agent 原生支持 ACP 就直接接入；不支持的，通过现有适配器转换。

ACP 指 Agent Client Protocol。统一的是通信入口与共同交互处理，不是把不同 Agent 变成同一个 Agent，也不是重新发明一个协议。

当前与候选对照完整候选架构新增、保留与移除

1 · 先看核心差别

改变的是“谁负责适配”：当前由 Farfold 直接处理三种原生协议；候选方案让 Farfold 处理 ACP，原生差异由 Agent 自己或 ACP 适配器承接。适配工作减少并可复用，但没有凭空消失。

3 · 相比当前，新增、保留和移除什么

变化 部分 实际意味着什么
保留 自有工作台与合理的专属交互 共用界面继续用；把事件来源改接公共接口，不要求把所有专属组件合成一个。
保留并完善 公共 Host 与数据身份 沿用项目、安装/连接、原生 Session 绑定、任务准入、草稿和诊断；适配新连接形态。
新增 公共 ACP 客户端 基于现有 SDK 做一套握手、请求、事件、能力和交互处理；同时接入 Farfold 的文件/终端等必要客户端回调。
新增 / 复用 Agent 注册与 ACP 接入定义 每个 Agent 声明启动命令、依赖、适配器和配置差异；优先使用已有 ACP 适配器，原生 ACP 直接接。
替换 三条原生工作通信路径 Pi RPC、OpenCode HTTP/SSE、Codex App Server 的 Farfold 直连实现由 ACP 路径替代；原生协议可以继续存在于外部适配器内部。
扩展 本机发现与按需安装管理 把两种安装来源接入同一套流程；补安装/依赖检查、更新、失败恢复与所有权。不是 ACP 协议自动提供的。
单独建设 Provider 一次配置、多 Agent 复用 公共存储与配置入口，加各 Agent 官方配置映射；模型与认证兼容性仍按 Agent 判断。
迁移后移除 被替代的旧实现与随包下载构建路径 删除重复原生通信、相应旧控制路径，以及 Pi/OpenCode 随主包分发的构建配置；保留仍需的原生配置/认证代码。用户数据不在删除范围。

“移除”指未来完成迁移后清理被替代代码，不是现在删除。旧会话和用户配置需要先明确兼容、保留与恢复规则。当前产品代码没有改动。

4 · 这条路线带来的工作，分清三类

因为采用 ACP 要做的公共 ACP 客户端、UI 事件与交互映射、Agent 启动定义、适配器接入、能力与扩展处理、旧会话衔接设计。
无论是否采用 ACP 都要做的本机发现、按需安装、版本与依赖、升级处理、身份绑定、错误定位、退出与恢复。
来自产品目标、需另外做的Provider 配置复用、已有账号与历史复用边界，以及各 Agent 专属交互的产品呈现。

5 · 在进入开发前，继续把这些位置画清楚

公共客户端和 Agent 专属适配，边界在哪里？

公共客户端统一 ACP 消息和常见交互；Agent 接入定义保留启动、配置、版本和扩展差异。协议转换优先交给已有适配器。若必需能力没有标准接口或可用扩展，先明确取舍，不默认另加一条原生控制通道。

用户已有安装，如何连接与升级？

找到并记住程序 → 检查版本、依赖和适配器 → 用户选用时启动 ACP 入口 → 握手并读取能力 → 完成认证 → 创建或恢复会话。握手成功不等于模型账号可用。升级自己的托管安装与升级用户本机安装分开处理；原有安装的代升级范围尚待确定。

原有会话和特色能力，迁移后如何保留？

会话始终绑定 Agent 安装/连接和原生 Session。适配器是否能恢复现有 Session、原生特色如何通过 ACP 暴露与展示，需要在设计中列清。不能把更换通信接口说成历史和功能自动完整迁移。

当前事实与候选接口的依据

本地源码：src/App.tsx 的三个工作台组件；src-tauri/src/runtime_supervisor.rs 的公共生命周期边界；pi_runtime.rs 的 RPC 启动；opencode_runtime.rs 的服务接入；codex_runtime.rs 的 App Server 通信与共享事件。以上描述当前实现，不代表候选方案已交付。

  • Zed 外部 Agent：ACP 接入与配置边界
  • OpenCode 官方 ACP 入口
  • Codex ACP 适配器：连接 App Server
  • Pi 社区 ACP 适配器

这是接口形式的依据，不是已经确认当前 Farfold 固定版本与所选适配器完全兼容。适配器版本与维护方选择尚未定案。
