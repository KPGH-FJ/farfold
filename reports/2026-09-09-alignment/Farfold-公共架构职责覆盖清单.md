# Farfold 公共架构职责覆盖清单

2026-09-10 · 对统一 ACP 候选架构的设计补充 · 不进入开发

**此前图中的“握手、能力、请求、事件、权限与提问”和“项目、会话绑定、生命周期、事件通知”只是概览，不是完整功能清单。**架构设计需要同时覆盖通信、Host 基础服务、公共工作台和按能力启用的工作界面。下列是本轮基础产品的设计核对范围，不声称穷尽未来所有 Agent 能力。

## 1. 公共 ACP 客户端：负责按协议交流

| 职责           | 具体包括                                                                         | 边界                                                                      |
| -------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 协议与连接     | 传输、初始化、协议版本协商、能力声明、请求与响应关联、错误、超时、断开           | Agent 程序从哪里来、谁启动它，属于 Host；协议通道如何读写属于客户端       |
| 认证交流       | 支持的认证方式、认证交互、认证失败与退出登录                                     | 本机凭据保存、原有账号是否复用、Provider 配置映射由对应 Host 服务负责     |
| 原生会话操作   | 新建、列举、加载/恢复、关闭、删除及会话信息更新                                  | 只启用选定协议和 Agent 实际支持的操作；本地列表与原生历史不是同一份数据   |
| 任务与消息     | 发送消息与附件、流式回复、完成/失败、取消；有明确支持时暴露运行中干预            | 不把普通发送伪装成原生 steering，不在重连后盲目重发任务                   |
| 内容与工具事件 | 文本、图片/资源引用、工具状态与输出、文件位置、diff、执行计划                    | 接收数据与渲染界面是两项职责；某 Agent 不提供的信息不能自行补造           |
| 用户交互       | 权限请求、结构化提问、选项与答案回传、取消时清理待答请求                         | 保留 Agent 给出的含义；工具授权、登录授权和文件审阅是不同操作             |
| 文件与终端回调 | 按所选协议及能力处理 Agent 请求的文件读取/写入、终端创建、输出、退出、终止与释放 | 客户端把请求交给 Host 的文件/进程服务；这不是 Farfold 再做一套 Agent 循环 |
| 配置与扩展     | Agent 提供的模式、模型/配置选项、斜杠命令、用量与上下文信息、扩展能力            | 依实际支持展示；保留未知消息与扩展的诊断信息，但不冒充已支持              |

“公共”意味着共用实现，各 Agent 连接、会话、认证及待处理请求仍须隔离。能复用现有 SDK 的协议代码应复用，Farfold 主要实现自身服务和界面之间的连接。

依据：[ACP 文档目录](https://agentclientprotocol.com/llms.txt)、[初始化](https://agentclientprotocol.com/protocol/v1/initialization)、[文件服务](https://agentclientprotocol.com/protocol/v1/file-system)、[终端服务](https://agentclientprotocol.com/protocol/v1/terminals)、[工具与变更内容](https://agentclientprotocol.com/protocol/v1/tool-calls)。本轮目录同时存在 v1 与 v2 草案；这是覆盖范围核查，不是选择 v2。后续设计须明确协议/SDK 基线，将必要功能、可选能力、扩展与草案分开，不能因为官网有文档就假设三个 Agent 已支持。

## 2. 公共 Host：负责本机资源、状态与可靠运行

| 职责                 | 需要设计的内容                                                                                     |
| -------------------- | -------------------------------------------------------------------------------------------------- |
| Agent 目录与安装     | 注册信息、本机发现、多版本选择、按需安装、适配器与依赖、兼容检查、更新/卸载及来源所有权            |
| 项目与工作环境       | 项目目录、工作副本、工作目录、环境变量、可用文件范围、同一工作区的并发约束                         |
| 连接与进程管理       | 启动/停止、初始化阶段、退出清理、崩溃恢复、连接代次与过期事件隔离；区分关闭窗口和结束任务          |
| 会话与持久化         | Farfold 会话到安装/连接及原生 Session 的绑定，标题、草稿、历史引用、重启恢复、删除范围与旧数据迁移 |
| 文件与终端基础服务   | 文件内容、文件变化观察、进程执行与资源释放，服务于 ACP 回调和工作台；不另加工具决策循环            |
| 工作区变更与审阅数据 | Git 状态与差异、基线、已有修改、未跟踪/重命名/删除/冲突文件；非 Git 项目的实际支持范围             |
| Provider 与凭据      | 公共配置与安全凭据引用、按 Agent 应用配置、账号复用边界、认证状态与模型可用性分离                  |
| 运行可靠性           | 状态快照和事件衔接、顺序/重复/丢失处理、大输出边界、未完成操作恢复、错误分类、日志脱敏与通知       |

每一项都要标记当前已有、需调整或新增，不能把这张表理解成重新开发全部基础设施。安装升级和认证复用等产品行为也不能由公共库替用户决定。

## 3. 公共工作台：负责呈现与操作

共同展示：项目与会话列表、输入与附件、消息与资源、工具进度、计划、权限与提问、模式与模型选项、连接/运行/错误状态、历史恢复入口、通知、设置、键盘与无障碍交互。

更专门的工作界面按能力启用：文件树、文件预览、代码 diff、终端输出、工作区变更列表、审阅状态与文件定位等。这些可以成为共享组件，不需要为每个 Agent 重写，也不需要让不支持对应操作的 Agent 展示无效入口。

不要只按“coding / 非 coding”硬分两套工作台：是否提供文件位置、diff、终端内容、计划等实际能力，才是显示某项交互的直接依据。Agent 特有交互保留扩展位置。

## 4. 代码变更展示：三段共同完成

| 数据 / 操作                            | 主要负责者           | 含义                                                       |
| -------------------------------------- | -------------------- | ---------------------------------------------------------- |
| Agent 报告的 diff、文件位置和工具状态  | ACP 客户端接收       | 描述某次工具操作及其状态，不保证涵盖工作区全部实际变化     |
| 工作区真实变更、文件内容和基线比较     | Host 的文件/Git 服务 | 可能含用户或外部程序已有修改，不能全部归因于当前 Agent     |
| 变更列表、前后对照、文件跳转、审阅标记 | Farfold 前端公共组件 | 呈现数据来源和操作含义；“已审阅”不等于授权、应用或撤销修改 |

ACP 标准工具内容已经可以携带 diff 和文件位置，但需要 Agent/适配器实际发送、客户端接收，以及前端实现渲染。[依据](https://agentclientprotocol.com/protocol/v1/tool-calls)

当前源码已有 `src-tauri/src/host_store/turn_changes.rs`：通过 Git 获取变更路径与状态，记录基线和归属状态；前端 `src/components/TurnChangesSection.tsx` 经 `SessionContextPanel.tsx` 呈现路径审阅。这证明已有公共基础，不证明完整逐行 diff 编辑、恢复或撤销已实现，也不是本轮安装应用验收。

“接受 / 拒绝 / 撤销”需要单独定义：有些 Agent 的修改已经落盘，不能把“接受”假装成应用修改；撤销还要处理用户随后编辑的内容。这属于设计待定项，本轮不新增操作、不修改文件。

## 5. 如何让下一版架构不再只是一张概览

每项共同能力补四个字段即可：**由谁负责、数据从哪里来、前端如何呈现、缺失或失败怎么办**。涉及协议能力再标记“基础必需 / 可选 / 扩展或待定”，涉及现有代码标记“保留 / 调整 / 新增”。

以开始工作、执行与干预、查看产物、退出与返回这条用户路径检查遗漏；不提前扩展跨 Agent 协作、LifeModel 或新 Runtime。此清单是设计补充，不是新开发计划或完整功能承诺。
