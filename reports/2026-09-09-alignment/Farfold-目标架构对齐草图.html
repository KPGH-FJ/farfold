Farfold 目标架构

一个自己的工作台，一层扎实的公共接入机制，一套公共 ACP 客户端。用户优先复用本机 Agent，也可以在工作台中按需安装；保留各 Agent 的原生能力。

一次连接：用本机 OpenCode 举例

1 · 找到安装找到本机程序；没有则按需安装。多个候选时选择并记住。
2 · 检查适配检查版本、依赖与接口支持。缺少适配器或需要升级时给出处理入口。
3 · 启动并接通选择工作时启动原生 ACP 模式或适配器，完成 ACP 握手，建立命令与事件连接。
4 · 开始工作确认模型服务可用，创建或恢复会话；工作台收发消息和原生交互。

自动发现不等于同时启动所有 Agent；接入本机安装通常是用这份程序启动新进程，不是接管用户已经打开的终端。

当前与目标，分开看

部分 当前基础 本次目标
工作台 一个前端，三个专属工作台组件，共享部分界面和 Host 机制。 继续共享公共部分，保留合理的原生差异；不以消除专属组件为目标。
通信路径 Pi RPC、OpenCode HTTP/SSE、Codex App Server。 统一由公共 ACP 客户端接入原生 ACP 或 ACP 适配器；不代表迁移已完成。
安装来源 Pi / OpenCode 随包；Codex 复用选定的本机安装。 主包不带 Agent 本体。统一支持本机复用与工作台按需安装。
Provider 配置与认证路径按 Runtime 分开。 兼容的 Provider 尽量一次配置、多个 Agent 复用。
公共中间层 已有生命周期、会话绑定、准入和事件通道；仍有专属控制路径。 按实际问题收敛公共机制，补齐安装来源、版本适配和配置复用。

看图时，优先对齐这三处

已有登录、配置和历史，要复用到什么程度？

复用程序不等于复用账号或历史。目标是减少重复操作，同时明确选择范围、不覆盖原有设置。具体边界仍需逐项确认。

版本不兼容，怎样处理？

能通过升级解决的，提供升级到兼容版本的路径。Farfold 管理自己的安装；用户原有安装可提示自行升级，是否提供代升级及其范围仍待确认。

哪些共用，哪些保留？

通用流程与 ACP 客户端共用；按 Agent 保留启动、配置与展示差异。优先复用现有 ACP 适配器，原生支持 ACP 的 Agent 直接接入。每个 Agent 的实际能力仍需验证，不保证任意版本、任意 Provider 都兼容。

Agent 继续拥有推理循环、工具与权限行为、原生会话和工作记忆。Farfold 中间层负责接入和产品公共机制，不另建 Agent 执行循环。本图聚焦本轮基础架构，暂不展开跨 Agent 协作与 LifeModel。
