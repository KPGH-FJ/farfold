# Farfold 技术路径与发展规划对齐报告

2026 年 9 月 9 日 · 产品研发对齐与商业计划书基础材料

## 1 核心判断与当前定位

Farfold 正在建设一个通用个人桌面 Agent 工作台。用户在 Farfold 自己的界面里选择项目和 Agent，完成代码、文档、研究整理等工作，查看真实执行过程、进行干预，并在之后继续原来的会话。各 Agent 是平等的可选项；产品的共同体验由 Farfold 提供，执行能力由接入的外部 Agent Runtime 提供。[S1]

**当前技术路径是：Tauri 2 桌面应用、React 与 TypeScript 界面、Rust Host、本地 SQLite，以及通过官方接口连接的多个外部 Runtime。** Farfold 管理桌面体验、工作目录、会话引用、事件呈现和恢复；Runtime 管理 Agent 执行循环、原生会话、模型调用、工具和原生权限。[S1][S4]

短期工作的重点已经确定：先把 Pi/OpenCode 的基础使用过程做扎实，再完成 Codex 的第三路接入和三路安装验收。长期方向是让用户在多个 Agent 之间保持稳定的工作体验，逐步探索任务交接、协作，并在独立 LifeModel System 成熟后承接集成。未来方向尚未变成当前开发承诺。[S2][S5]

这三个应用的版本字段目前都为 0.1.6，必须同时看应用名称、标识和可执行摘要。本次已读取三者的实际安装身份；能力结论来自对应构建的已有验收记录，本报告没有重新执行模型任务。[S2][S3][S6]

### 这份报告用于对齐什么

## 2 当前技术路径与架构取舍

### 桌面产品如何连接 Agent

用户操作 → Farfold React 界面 → 类型化 Tauri 命令与事件 → Rust Host 公共机制 → Runtime 专属适配器 → 官方 Runtime 接口 → 原生 Agent 执行系统。

结果沿反向链路返回界面。模型服务由对应 Runtime 调用；Farfold 的基础工作链路没有另建一个决定 Agent 下一步行动的执行循环。[S1][S4]

| 层次       | 当前技术                          | 主要职责                                               |
| ---------- | --------------------------------- | ------------------------------------------------------ |
| 桌面外壳   | Tauri 2，当前 Apple Silicon macOS | 窗口、应用生命周期、系统对话框、原生进程连接           |
| 用户界面   | React 19、TypeScript 5.9、Vite 8  | 会话与项目导航、输入、执行过程、原生交互和错误恢复     |
| 本地 Host  | Rust，类型化命令和事件            | 程序与连接管理、身份检查、任务准入、事件分发、恢复     |
| 本地数据   | SQLite，rusqlite，事务迁移        | Farfold 会话索引、项目与工作副本、草稿、绑定及自身状态 |
| Agent 执行 | Pi、OpenCode、Codex 专属适配器    | 经官方接口使用 Runtime 的真实能力                      |

### 三条接入路径

| Runtime  | 固定版本与获取方式                                        | Farfold 使用的接口                                          |
| -------- | --------------------------------------------------------- | ----------------------------------------------------------- |
| Pi       | 0.84.3，随应用携带，校验版本和 SHA-256                    | stdio 上的 JSONL RPC；配套能力桥接使用同版本 Pi 包          |
| OpenCode | 1.15.13，随应用携带，校验版本和 SHA-256                   | 官方 Server，HTTP 请求与 SSE 事件流                         |
| Codex    | CLI 0.143.0，复用用户显式选择的官方 arm64 程序或 npm 入口 | Farfold 自有 stdio App Server，关联请求、通知与原生反向请求 |

以上路径已在源码中对应到独立模块；Pi 和 OpenCode 的下载脚本固定归档与程序摘要，Codex 保存程序及解释器等启动引用，启动前验证。Farfold 不安装或升级用户的 Codex CLI。[S4]

Pi 的 Agent 工作通过 RPC 执行；Provider、模型、认证和资源发现还通过同版本能力桥接暴露给界面，不能把它理解为 Farfold 自建模型网关。官方接口分别确认了 Pi 的 RPC、OpenCode 的 Server、Codex 的 App Server 这三种集成方式。[S7][S8][S9]

### 采用这条路径的原因及代价

这一设计让 Farfold 可以集中改善完整桌面体验，同时保留各 Runtime 已有的模型、工具和生态能力。代价是必须持续处理不同协议、状态和恢复语义，并承担固定版本核验与上游变化带来的维护工作；接入数量增加并不会自动带来统一体验。

ACP 可以作为未来对象的官方接入选择，但当前三路并非统一采用 ACP。SDK、RPC、Server、ACP 也不是互斥分类，最终应按目标 Runtime 的官方支持和能力保留程度选择。协议共同化只能减少部分通信差异，不能代替任务结果和恢复验收。[S1][S5][S10]

## 3 共同机制与数据边界

### 统一体验保留原生差异

当前源码已有公共工作台状态、导航与开始工作容器，Pi、OpenCode、Codex 分别提供专属工作台组件。Rust 侧已有生命周期适配接口、会话控制、任务准入、事件路由与交互登记。公共层仍存在按 Runtime 派发的实现；这是一套正在验证和完善的接入架构，尚不能称为任意 Agent 即插即用的平台。[S4]

共同界面应让用户始终看清项目、工作目录、Agent、模型、当前任务和可执行操作。Pi 的资源信任、steering 与 follow-up，OpenCode 的原生权限，Codex 的命令审批、文件审批和 Plan 提问，继续由各适配器表达真实语义，不因界面统一而伪装成完全相同的能力。[S1][S2]

### 会话和工作文件如何保持连续

一个 Farfold 会话固定绑定 Runtime 产品、具体安装与连接、工作项目和原生 Session。恢复时必须核对原生身份与目录；切换 Runtime 会打开或新建另一个会话，不移植原有 Agent 的不透明内部状态。[S1][S4]

| 数据或权力           | 归属                         | 对产品行为的要求                                 |
| -------------------- | ---------------------------- | ------------------------------------------------ |
| 项目文件与工作副本   | 用户；Farfold 管理选择和引用 | 明确实际目录，保护用户文件，控制并发冲突         |
| 原生历史与工作记忆   | 各 Runtime                   | 经官方接口续接；缺失时保留事实和绑定，不静默新建 |
| 导航、草稿、会话引用 | Farfold Host                 | 持久保存，恢复不自动重发用户输入                 |
| 认证与模型配置       | 对应 Runtime 的原生机制      | 区分程序可用、已认证、模型可选和真实请求成功     |
| 个人 LifeModel       | 用户与 Farfold 的治理边界    | 来源有据，用户批准后进入正式模型；当前原型冻结   |

全应用最多两条活动任务，同一 Working Copy 排他；当前 Codex 每个连接最多一个活动任务。这些机制用于限制容量和文件冲突，不等于已经实现多 Agent 协作。[S2][S4]

### 状态必须能解释真实后果

发送被接受、任务正在运行、等待用户、请求停止、确认结束和结果未知是不同状态。断流或请求超时不能证明任务已停止；Stop 也不撤销已经发生的文件修改。事件带有来源、进程代际和序号，旧进程或其他会话的迟到消息不能恢复旧交互。原生事件保留受有界缓冲和大小上限约束，丢失或截断需要明确表达。[S2][S4]

当前开发源码与 P6 QA 使用 Host schema 8，新增系统安装的启动定位与验证信息；第一交付仍以 schema 7 为界。应用升级需要与对应数据成对备份、实际恢复。Host 导出没有包含全部原生历史、认证和项目文件，不能单独当作完整备份。[S2][S3]

## 4 短期规划与验收重点

### 交付一完善 Pi 与 OpenCode 的完整使用过程

已批准的 P0 至 P3 围绕开始工作、执行干预和返回续接展开。目标是让用户无需理解底层连接细节，就能选对项目与模型、开始真实工作、看懂进度、及时干预，并在出错或退出后继续原来的任务。[S2]

- **开始工作：** 统一新建和打开入口，明确配置、认证、模型和请求状态；错误保留草稿，不能暗中替换目录、模型或 Agent。
- **执行干预：** 稳定呈现工具、回答、错误和等待用户的交互；Stop 根据原生终态确认，保留各路真实的转向、跟进和审批能力。
- **返回续接：** 保存标题、草稿和选中状态，按原生 ID 核对历史；目录冲突指出占用任务，缺失会话不伪装成空白新会话。
- **交付闭环：** 在同一个安装构建中回归两路能力，验证应用与数据的成对恢复，完成正式路径检查；被替代的控制路径在相同切片删除。

这些方面已有大量源码与 Dev 安装修订记录，但活动计划中的 P1 至 P3 总体验收仍未关闭，不能用后续 Codex 进展自动宣布交付一完成。[S2]

### 交付二接入 Codex 并验证三路共存

P4 的固定接口核验已取得官方源码、协议和原生试验证据。P5 已在 Dev 安装中验证 ChatGPT 登录、文本和文件任务、命令与文件审批、Plan 提问、转向、停止与原生线程续接。P6 正在进行独立 QA 和最终交付核验。[S2]

Codex 首版有明确范围：固定 0.143.0，Plan 提问采用已批准的实验 API，Default 模式的开发中提问特性关闭；冷历史只恢复官方接口实际返回的内容，并提示可能缺少命令详情。API key 入口目前仅有接口和测试依据，没有真实账号请求验收。完整 Skills/MCP/插件配置管理、远程执行、自动化及图片视觉输入不能包含在本次已交付声明中。[S2][S3]

### 接下来应完成的收尾

## 5 长期方向与 LifeModel 分工

长期应围绕用户工作能否持续、能否选择合适的 Agent、能否控制自己的数据来发展。下面区分已对齐方向和后续建议；具体投入与实施顺序仍需另行确定。[S1][S5]

### 方向一把工作台做成稳定的日常入口

用户可以跨天继续项目，辨认任务做了什么、哪些操作还在进行、哪里需要自己判断。跨 Runtime 的界面与恢复应越来越一致，原生能力的差异则越来越清楚。完成三路交付后，建议以真实任务中的中断恢复、重复配置、草稿丢失、错误目录和人工返工为主要改进依据。

Farfold 当前定位覆盖通用个人工作，不局限于写代码；但每一类扩展任务仍须有实际结果证明。连接了一个有浏览器或文档工具的 Runtime，不自动证明 Farfold 已提供完整的浏览器操作或文档制作体验。

### 方向二形成可维护的多 Runtime 接入能力

已对齐的方向是复用公共会话、连接、事件和工作台机制，并保留专属能力。Codex 是验证这套架构能否承受差异的第三个对象。后续是否加入第四路，应看它是否带来已支持对象不能覆盖的用户价值，以及官方接口是否支持可靠控制与恢复；当前没有第四路实施承诺。[S1][S2]

建议让新接入的成本主要落在适配器及其验证上，而不是反复复制整套工作台。是否实现这一点，应通过新增和维护切片中的实际改动判断，不能仅依据有一个名为 Adapter 的接口。

### 方向三承接独立 LifeModel System

LifeModel System 由独立团队研究，研究对象是如何从授权来源形成、维护和使用个人理解。个人 LifeModel 是用户经该系统形成的模型；Farfold 是信息来源与应用入口之一，承担未来的系统集成和用户交互。其范围不应被现有最简原型或偏好键值表限定。[S1][S5]

Farfold 当前的 LifeModel 原型冻结，保留主界面入口、默认关闭和既有 opt-in/Proposal 语义。普通工作不依赖启用它，Codex 首版既不贡献也不消费 LifeModel。Auto Research 是研究组织与实验框架，LifeModel 是独立研究对象，Farfold 是产品实现；三者的进展和完成判断必须分别记录。

未来集成仍遵循：授权来源 → 候选理解 → 原子 Proposal → 用户确认、修改或拒绝 → 正式个人 LifeModel → 相关性选择与预览 → 官方 Runtime 上下文通道。[S1]

基础运行、贡献个人理解、使用个人理解是三个独立能力。原生会话记忆继续属于 Runtime；长期理解只有在来源可追溯、用户可控制、实际任务受益得到验证后，才具备扩大使用的依据。当前没有长期效果已经证明的结论。[S1][S5]

## 6 未来发展想象力与验证方式

以下场景用于说明产品可以往哪里发展。跨 Agent 交接、共享任务协作和 LifeModel 生态关系来自既有对齐记录；它们均不是当前已实现能力，也没有因此进入本轮实施范围。[S5]

### 从单次会话走向跨 Agent 的工作连续性

用户先让 Agent A 调研一个主题，再让 Agent B 接着形成报告。Farfold 可以探索把任务目标、已确认要求、来源、成果文件和未完成事项组织为可检查的交接材料，让用户减少重新说明背景的工作。

真正的价值在于接手者能继续做对事情。交接的是可获取的材料和任务状态，不承诺迁移 Agent 的完整内部会话或模型推理。研究必须解决材料遗漏、来源和版本、文件可访问性及授权范围；当前 Codex 冷历史的命令详情缺口，也是交接不能假设历史完整的具体例子。

建议验证：在相同任务上比较手动交接和 Farfold 辅助交接，记录重复说明、遗漏、返工、耗时与费用。只有用户负担下降且质量没有明显损失，才值得扩大场景。

### 从分别执行走向共享任务空间中的协作

一个 Agent 查资料，一个提出质疑，另一个综合成稿；用户在同一个任务界面查看分工、阶段成果和待决定问题。组织者可以由用户选择或更换，它是任务角色，各参与者仍使用自己的 Runtime 和原生会话，也不要求使用不同模型。

这需要明确消息交给谁、成果如何共享、文件冲突如何避免、任务失败后如何恢复以及何时停止。两个任务同时执行、多个回答并排展示，都不足以证明协作成立。任何未来协调机制也必须保留 Runtime 对自身 Agent loop 的所有权，不能借此悄悄建立替代执行引擎。

建议先比较边界明确的双 Agent 任务与单 Agent 基线，测量质量、用户介入、耗时和费用；有效后再讨论参与者数量与自主程度。交接与协作可共享部分基础设施，但不要求先后实施，也不以启用 LifeModel 为前提。

### 从桌面工作入口走向个人理解的应用入口

如果独立 LifeModel System 能可靠形成用户授权的长期理解，Farfold 可以让符合条件的不同 Agent 使用同一份可审查的个人背景。例如，用户换 Agent 起草报告时，可以选择使用自己已确认的表达要求和长期目标，减少重复设置，同时保留本次任务覆盖这些背景的权利。

更远的系统设想还包括授权手机截图、录音转录等来源，以及其他 Agent 产品插件、机器人和智能设备等使用出口。这些属于 LifeModel System 的未来生态范围，尚无可据此宣称已交付的跨设备接口；也不意味着 Farfold 当前需要开发手机端或硬件。[S5]

### 值得积累的产品能力

从这条路径可以推导，Farfold 有机会积累的长期价值包括稳定的工作连续性、清楚的能力差异、可信的恢复与控制，以及可选的个人理解应用体验。这些是产品价值假设，不能用接入数量或历史数据量直接证明。它们最终要通过用户是否持续使用、是否减少返工、是否愿意在更长任务中依赖 Farfold 来判断。

## 7 主要约束与对齐事项

### 当前最需要避免的判断偏差

| 问题                        | 对产品判断的影响                 | 当前处理或后续验证                           |
| --------------------------- | -------------------------------- | -------------------------------------------- |
| 开发版与日用版进展不同      | 代码完成可能被误报为用户已可用   | 以应用标识、摘要、环境和同构建结果区分       |
| 固定 Runtime 的接口缺口     | 原生会话存在不代表全部历史可展示 | Codex 首版声明官方冷历史范围，不另建历史权威 |
| 真实使用尚不充分            | 工程任务成功不代表日常体验成熟   | 补本人任务、第二成员与第二 Mac 验收          |
| 异常后的执行状态未知        | 重发可能造成重复执行或文件冲突   | 保留占用、草稿和绑定，核对原生终态后恢复     |
| 过早扩大 Runtime 或协作范围 | 增加维护成本并拖延基础交付       | 先收口三路，未来候选单独验证与决策           |

### 性能应按用户等待的完整过程理解

已有 6fe6 Dev 构建在一台 M4、16 GiB、macOS 15.6 设备上完成 20 次冷恢复。记录中的冷进程可交互 p95 为 372 ms，Runtime 就绪后历史恢复的 Pi/OpenCode/Codex p95 分别为 508/1021/86 ms。但 Codex 有一次恢复为 2933 ms，而且程序校验另计的 p95 约为 11.30 秒。[S2]

因此，不能把 86 ms 当作 Codex 从启动到可工作的总等待时间。这些数字也不能用于宣称 QA release 或第二台机器具有同样性能。它们更适合指导下一轮受控测量，分别观察程序检查、连接初始化、历史恢复、界面呈现与模型等待。

### 已确定和仍待决定的事项

**保持执行的共识：** 两次内部交付顺序；自己的桌面 UI/UX；官方固定版本接口；Runtime 平级；用户数据保护；LifeModel 原型冻结且可选；人工验收与工程证据分开。[S1][S2]

**本次报告建议的后续讨论：** 三路内部交付完成后，优先验证跨 Agent 交接还是双 Agent 协作；怎样选择能体现价值的真实任务；以哪些质量和用户负担指标决定继续投入。这些建议不构成新排期。

公开发行、自动更新服务、Developer ID 与公证不是当前内部里程碑的阻塞条件。当前更新端点和公钥未配置，不能宣传自动更新可用。Windows、Linux、云同步、计费、远程执行与第四路 Runtime 均没有纳入当前实施范围；以后是否投入，需要独立的用户价值与工程判断。[S1][S2][S4]

### 可直接用于团队介绍的口径

Farfold 是一个独立的个人桌面 Agent 工作台，通过官方接口接入不同 Agent，提供统一的项目、会话、执行与恢复体验。当前内部日用基线支持 Pi 和 OpenCode，Codex 开发版已有真实安装验证，正在完成独立 QA 与交付。近期先把基础功能和三路体验做扎实；未来探索任务交接与多 Agent 协作，并在独立 LifeModel System 成熟后承接可选集成。

## 8 商业计划书可复用的业务逻辑

本节为商业分析与待验证假设，不代表新增研发承诺或已经成立的经营事实。Farfold 当前可展示的进展主要是产品实现和工程验证；尚不能以安装测试次数代替真实用户、留存或收入。

### 目标用户与切入场景

建议首先验证已经使用 Agent、拥有真实本地项目、需要持续推进任务的个人专业用户。开发者与技术创作者适合作为第一组候选，因为当前代码读写、项目目录与原生会话能力最接近他们的工作；报告写作、研究整理等知识工作者可以作为相邻验证群体。这个切入次序是本报告建议，不是既定市场结论。

| 候选用户               | 需要验证的具体痛点               | Farfold 可检验的价值                         |
| ---------------------- | -------------------------------- | -------------------------------------------- |
| 多 Agent 的个人开发者  | 项目与会话分散，配置和恢复复杂   | 在统一入口完成真实开发工作，保留原生差异     |
| 技术创作者与独立研究者 | 任务跨天，资料与成果需要反复整理 | 保存工作连续性，完成文档与代码混合任务       |
| 更广泛的知识工作者     | 专业 Agent 的使用门槛较高        | 通过易理解的工作台获得可靠产出；适配程度待验 |

早期可以从一条完整的工作路径验证需求：选一个已有项目，完成真实任务，期间出现一次干预或中断，下一次启动后继续同一会话。它比“支持多少个模型或 Agent”更能检验用户是否得到持续价值。

### 价值主张与替代方式

可用于商业计划书的价值主张是：**让个人在一个可控制、可恢复的桌面工作台中使用不同 Agent，减少配置、切换和续接工作的负担。** 后半句是价值假设，需由真实使用数据证明；当前可以证明的是相关产品机制和部分安装任务已经存在。

用户可能继续直接使用某个 Agent 的官方客户端、CLI 或编辑器集成，也可能使用其他多 Agent 工作台。Farfold 必须说明为什么这些用户还需要另一个工作入口：统一的桌面体验是否更好，核心能力是否保留，跨天工作是否更可靠，以及未来的交接是否真正节省时间。不能因为采用了多个 Runtime，就推导产品具有独占能力。

差异化应通过同任务、同 Runtime 和相近模型条件下的比较来证明。当前没有足够依据声称 Farfold 的模型质量、执行速度或成本优于所有替代产品，也不宜以“无缝接入任意 Agent”描述现状。

### 商业模式候选与成本边界

个人软件订阅或付费许可可以作为早期验证候选：用户为工作台体验、连续性和可靠性付费，Runtime 与模型服务费用的承担方式另行明确。高级交接或协作能力可以成为未来增值假设，但需要先证明价值；团队管理与企业销售涉及权限、部署、协作和支持体系，目前没有相应产品承诺。

当前产品没有计费实现与定价证据。后续应验证用户是否愿意在已有模型或 Agent 费用之外为 Farfold 付费，以及订阅、买断或其他许可方式是否适合。成本模型至少区分 Runtime 接入与升级维护、QA、分发与支持、未来在线服务和模型成本；不能仅凭调用用户自己的账号，就认定软件成本接近零。

## 9 商业验证路径与需要补齐的材料

### 用现阶段能力验证真实需求

建议先完成内部使用和第二台 Mac 验收，再邀请少量符合候选画像的用户，用自己的项目和账号持续工作。当前阶段应观察他们能否独立开始、是否在后续工作日主动返回，以及哪些问题迫使他们回到原生客户端。这是后续验证建议，尚没有已批准的招募规模、预算或时间表。

早期获客可以测试开发者与创作者社区中的具体任务演示、定向邀请和真实用户推荐，内容应展示完成任务与恢复过程。渠道效果须用实际激活和持续使用衡量，不预设存在自然增长或确定的获客成本。

### 商业计划书需要补齐的证据

| 要回答的问题           | 需要收集的材料或指标                                | 当前证据状态                         |
| ---------------------- | --------------------------------------------------- | ------------------------------------ |
| 谁最需要这个产品       | 访谈、工作观察、用户实际使用的替代方式              | 候选画像；尚未形成需求样本           |
| 用户能否独立获得价值   | 首个真实任务完成率、配置耗时、中途退出原因          | 有工程任务；独立人工样本待补         |
| 是否形成持续使用       | 按用户群观察次周与后续留存、工作日复用、恢复成功率  | 未形成可报告的留存数据               |
| 是否值得付费           | 价格访谈、真实付费试验、续费与流失原因              | 未验证定价和收入                     |
| 市场有多大             | 明确地区、画像与付费产品类别后的可靠市场来源和测算  | 未测算，不填写无来源 TAM/SAM/SOM     |
| 单位经济是否成立       | 获客、支持、维护和在线服务成本，收入与毛利口径      | 无经营基线，无法推导 LTV/CAC         |
| 技术边界是否可商业持续 | 各 Runtime 许可、分发、认证条款及官方接口持续性复核 | 工程路径已核验，仍需商业用途专项确认 |
| 执行与资金如何安排     | 实际团队分工、招聘、预算、现金消耗和资金用途        | 本次没有可核验材料，不代填           |

上述指标首先需要统一口径。例如，任务完成应有可核对的结果，不能只统计模型返回；恢复成功必须继续同一原生会话，不能把新建成功算入；付费意愿与实际支付应分别记录。产品数据采集也应符合用户授权和隐私约定。

### 长期竞争力需要怎样证明

可积累的优势包括：跨 Runtime 适配和回归经验、异常状态处理、稳定的任务连续性，以及用户认可的工作方式。它们可能提高复制和维护的成本，但现阶段还不是已经证明的壁垒。Runtime 官方产品扩展自身 UI、协议变化或同类工作台改进，都可能缩小体验差异。

LifeModel 带来的个性化增益同样需要独立研究与任务验证，不能在商业计划书中直接写成已建立的数据壁垒。用户对数据的所有权、可审查性和迁移能力仍应保留。若未来协作成立，其价值也必须覆盖额外模型消耗、延迟和用户监督成本。

后续商业计划书可按“用户问题、产品价值、已有进展、差异化、发展路径、商业模式、经营指标、团队与资金用途”组织。本报告可支撑产品与工程部分；市场、用户、价格、增长、财务及团队材料仍须补齐，并保留事实与假设的边界。
