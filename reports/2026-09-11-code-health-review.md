# Farfold 代码健康度审查

审查日期：2026-09-11。范围：当前工作目录的结构、关键控制链路、测试与开发管理。开发任务仍在修改代码，因此这是本轮读取与测试时的快照，不是固定提交的完整逐行审计，也不是正式安装版验收。本报告不是第二份活动计划。

## 结论

**已有可继续建设的基础，但新架构迁移区出现明显的复杂度集中和状态耦合，需要边推进边收敛。当前不宜将 OpenCode 实验实现直接复制到其余 Agent，也没有证据支持推倒重写整个项目。**

代码混乱主要集中在「谁判断当前连接、当前任务、操作是否完成」和「多个入口如何操作同一个连接」，并非所有模块都混乱。共享 UI 与 Agent 专属逻辑并存本身符合产品要求；问题是公共生命周期处理尚未形成足够清楚、可复用的边界。

## 审查发现（按优先级）

### H1 · P1：ACP 前端过滤缺少连接代次，旧消息可能污染重连后的会话

- 位置：[OpenCodeWorkspace.tsx](/Users/tw/Desktop/farfold/src/components/OpenCodeWorkspace.tsx:1065)、[host-shadow.ts](/Users/tw/Desktop/farfold/src/runtime/host-shadow.ts:86)。
- 当前事件过滤核对 product、installation、adapter、build、connection；OpenCode 工作台明确只给非 ACP 事件做 generation 检查。
- 同一连接和 native Session 重启时，这些固定身份可以不变，generation 已变化。当前 reducer 只再检查 native Session，不能挡住旧代次。
- 本轮对源码函数做内存执行复现：当前绑定 generation 2、旧事件 generation 1，固定身份和 native Session 相同；过滤返回 true，旧 assistant 文本进入 timeline，并把 isWorking 设为 true。
- **证据边界：这是函数链路复现，尚未在安装应用中人为制造同样的迟到消息。**
- 修正：用当前连接代次和操作归属约束事件投影，同时保留合法 session/load 早期回放。不能简单恢复此前会丢失回放的 view-scope 暂停过滤。
- 验收：重连同一 Session 时，旧代次 chunk、权限和终态不污染新会话；新代次早期历史不丢；失败和断线保持真实状态。

### H2 · P1：同一 OpenCode 工作台承载多套启动入口和状态判断

- 位置：[OpenCodeWorkspace.tsx](/Users/tw/Desktop/farfold/src/components/OpenCodeWorkspace.tsx:1216)、[Provider 设置入口](/Users/tw/Desktop/farfold/src/components/OpenCodeWorkspace.tsx:2562)。
- 普通 Server 状态、ACP 状态、当前 Host binding、conversation.isWorking、submitting、transition、reconciling、acpBusy 分别维护；实验新建、managed 新建、普通新建和侧栏恢复各有流程。
- managed ACP 新建因任何 ACP running 状态被禁用；普通开始入口仍按 bundled OpenCode 的 available 状态判定。不同入口的连接来源和操作条件尚未统一。
- 最新安装 QA 已记录：新建/停止点击未带来状态变化、managed 新建被 running/unmanaged 状态禁用。该样本尚未排除 CUA 操作问题，不能仅凭它断言按钮实现必然失效；源码中的多入口耦合是已确认事实。
- 修正：保留 Runtime 差异，但把当前连接身份、操作生命周期与终态判断收敛到一个可测试的控制边界，界面消费其结果。设置页管理配置，不另行成为一套连接控制权威。首路验证后按切片删除被替代路径。

### H3 · P2：项目入口契约仍指向旧阶段，开发方向有两个版本

- 位置：[AGENTS.md](/Users/tw/Desktop/farfold/AGENTS.md:62)、[PRODUCT.md](/Users/tw/Desktop/farfold/PRODUCT.md:58)、[活动计划](/Users/tw/Desktop/farfold/plans/runtime-neutral-lifemodel.md:1)。
- 活动计划已经明确统一 ACP、统一 Provider、本机优先与按需安装；AGENTS 的 Current direction 和 PRODUCT 的 Runtime Contract 仍主要描述旧的两次交付、Server/App Server 选型及不安装 Codex等阶段约束。
- 历史事实需要保留，但应明确标为历史基线，并在入口写清最新阶段目标、迁移边界与唯一活动计划。否则新任务容易遵循旧方向，现有任务也可能把过渡路径当永久架构。
- 本轮未擅自修改产品契约；建议执行任务在既有用户授权范围内同步三份入口材料，不重新发起架构选择。

### H4 · P2：高风险组合流程缺少可重复的自动化回归

- 全量前端测试通过，但没有 PiWorkspace / OpenCodeWorkspace / CodexWorkspace 的直接工作流测试；现有组件目录测试主要是展示、纯函数或静态渲染。
- 近期实际出现过：一轮历史通过而多轮合并、能力更新误当终态、取消确认后永久占位。部分原测试反而断言错误状态，说明问题不仅是测试数量，还包括断言依据。
- 修正：围绕「新建→配置→发送→权限/取消→恢复→下一轮」补少量高价值集成测试，重点控制响应和事件先后顺序、旧回执、连接替换与失败重试；以协议和用户行为为标准，避免测试只是照抄实现。
- 安装应用验证仍保留，自动化组件/Host 测试不能替代真实 Runtime 与产品界面验收。

### H5 · P2：改动长期混在工作目录，回归定位和回退成本增加

- 审查时 HEAD 仍是 9 月 7 日的交付提交；有 81 个 tracked 修改、2 个 tracked 删除，以及 283 个未跟踪文件（含报告/配置/代码，不能全算应用源码）。
- 这些包括历史交付和本轮开发，不能全部归责于当前阶段，也不能仅凭未提交判定代码质量差。
- 但当前很难精确回答某一功能经过哪些验证、哪些改动能一起回退；工作区日志与安装包证据不等于版本库已有可恢复的开发检查点。
- 修正：先核清现有改动归属与敏感文件排除，再按可验证工作包形成局部检查点；不要盲目全量提交、重置或清理。保留唯一活动计划，将历史验证记录与当前状态清楚区分。

## 建议推进顺序

1. 在当前取消与入口工作包中解决 H1 / H2，补旧回执和冷恢复组合测试；不要等复制到三路后再治理。
2. 同步 AGENTS / PRODUCT 与当前活动计划；核清工作目录改动，形成可验证检查点。
3. 首路用户流程通过后，提取公共连接与操作控制，保留协议/Agent 特殊语义；删掉对应已替代入口和判断。
4. 再复用到 Pi / Codex，推进安装与 Provider 完整覆盖，最后做三路同一安装包验收。

**总体判断：基础可用，迁移区偏乱，可靠性证据尚不足以交付；适合定向治理后继续推进，不适合边堆新入口边扩 Agent。**
