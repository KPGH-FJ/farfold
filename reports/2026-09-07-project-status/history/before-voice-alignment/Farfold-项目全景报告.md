## Farfold 产品战略与项目全景报告

产品使命 · LifeModel · 商业与技术路线 · 当前交付事实

> 让不同 Agent 持续理解同一个人，在用户掌控下，把工作接着做、协同做好。

Farfold 希望成为一个以用户自己的 LifeModel 为长期核心、能连接多种 Agent Runtime 的个人智能工作台。统一界面让不同 Agent 可用；长期用户理解让它们更懂你；受控协作让它们逐步能一起完成更复杂的工作。

今天，这一愿景已有第一段工程基础：0.1.6 内部 macOS 安装版能够承载 Pi 与 OpenCode 的原生会话和文件任务。跨 Runtime LifeModel 已有治理原型与历史 QA 证据，但长期效果尚未证明。广泛 Runtime 接入、跨 Runtime 委派和主动持续服务仍属于后续方向。

## 01 使命：为用户建立持续的智能工作环境

先说要成为什么，再说今天实现了多少

### 建议用于对外介绍的产品定义

> Farfold 是一个面向个人的智能工作台：用户可以选择不同 Agent 来做事，并让经过自己确认的长期理解在这些 Agent 之间持续发挥作用。

它要解决的根本问题是：AI 能力持续变化，用户却不应每换一个工具，就重新解释自己的背景、习惯、长期目标和约束，也不应为了使用不同 Agent 而重新学习一套完整工作方式。Farfold 将稳定的用户界面、个人理解和工作连续性留在用户这一侧。

### 使命可以拆成三项任务

| 任务         | 用户获得什么                                   | 长期建设对象                            |
| ------------ | ---------------------------------------------- | --------------------------------------- |
| 让能力可选择 | 按任务选择合适的 Agent，保留真实差异与控制权。 | 统一 Farfold UI + 可验证的 Runtime 接入 |
| 让理解能积累 | 确认过的偏好、事实和长期约束能够被适当复用。   | 用户拥有、跨 Runtime 的 LifeModel       |
| 让工作能持续 | 跨天继续工作，逐步实现交接、分工和成果汇总。   | 原生会话连续性 + 受控协作与结果验收     |

### 未来理想体验

用户围绕“我要完成什么”工作，Farfold 帮助呈现可用 Agent、相关个人上下文、实际进度和结果。用户始终能知道谁在做、用了哪些信息、改了什么、哪里需要自己决定。执行步骤和工具选择仍由外部 Runtime 的 Agent loop 负责。

“通用个人产品”是长期范围；当前文件、代码与文档工作是可验证的起点。是否先聚焦技术用户或更广泛知识工作者，需要通过本轮对齐与试用确认，不把首版能力局限写成永久定位。

依据：PRODUCT.md Purpose / Ownership / LifeModel；2026-08-30 至 09-02 的产品对齐记录；2026-09-07 用户本次方向。使命句为本报告的归纳表述。

## 02 用户、痛点与第一批使用场景

目标用户假设：先服务高频知识工作者，再扩大覆盖

建议首先观察经常在多个 AI 工具之间切换、需要持续处理项目和交付物的人：开发者、研究者、产品与运营人员、独立创作者。它们是可测试的切入人群，不代表这些群体已经被访谈验证。小团队可以是试用单位，但个人 LifeModel 不因此变成团队共有资产。

| 真实问题假设            | Farfold 的回应                                     | 需要验证的结果                               |
| ----------------------- | -------------------------------------------------- | -------------------------------------------- |
| 工具分散、操作不同      | 统一项目、会话、进度、权限与恢复入口。             | 是否减少找会话、切应用和排障的时间。         |
| 每次都要重复介绍自己    | LifeModel 保存经过确认的稳定理解，按任务选择使用。 | 是否减少重复解释和纠正，同时不带入无关信息。 |
| 换 Agent 就丢上下文     | 保持原生会话；未来用可见的交接材料连接新会话。     | 接手者能否理解目标、事实和未完成事项。       |
| 产物“做完”但不可用      | 强化成果展示、检查和人工接受回路。                 | 可用产物比例与返工次数是否改善。             |
| 多 Agent 一起做反而难管 | 未来提供范围明确的委派、状态、权限和结果汇总。     | 总时间、质量与成本是否优于单 Agent。         |

### 建议优先验证的三类任务

① 一个代码或网页项目持续迭代并检查最终效果；② 同一项目的资料整理、分析和报告制作；③ 跨数天继续一项工作，复用个人输出偏好并由另一 Agent 复核。这些任务能同时检验文件工作、连续性和个人理解的价值。

早期访谈应问“你最近一次重复解释、丢失进度或人工搬运上下文发生在哪里”，让用户拿真实任务演示。暂不把市场规模、付费意愿或行业需求强度写成已有事实。

本页为用户与场景假设。当前已观察到的真实使用问题详见后半部分 UI/UX 与风险章节。

## 03 LifeModel：长期产品价值的核心

它承载关于用户的理解，而执行能力可以持续更换

LifeModel 的角色是保存并维护“这个用户长期希望怎样工作、有哪些稳定事实和约束”。例如输出习惯、长期研究方向、明确的工作边界。来自不同 Runtime 的陈述可以形成来源；经过用户确认后，合格的其他 Runtime 也能按需使用。

| 概念                | 负责什么                                           | 与 LifeModel 的关系                              |
| ------------------- | -------------------------------------------------- | ------------------------------------------------ |
| Runtime 工作记忆    | 这次任务进行到了哪一步，工具调用和原生历史是什么。 | 继续由 Runtime 管；不整体搬入个人模型。          |
| 项目上下文 / 知识库 | 项目资料、需求、文件、会议结论与工作产物。         | 可以支持任务，但不是所有项目事实都属于用户事实。 |
| LifeModel           | 经过确认的稳定事实、偏好、约束和工作方式。         | 跨 Runtime、由用户掌控、按相关性与范围使用。     |
| 协作任务状态        | 谁负责哪一段、依赖什么、产物在哪里、是否完成。     | 用于协作调度；不能冒充长期个人理解。             |

### 为什么它是核心

统一入口解决“在哪里使用 Agent”；LifeModel 要解决“为什么这些 Agent 能持续为同一个人服务”。它把个人积累从特定供应商或单个会话中分离，可能成为用户长期保留 Farfold 的原因。这个价值需要行为数据证明，不能仅由一张记忆表或一套审批流程证明。

### 为什么核心仍然可以是可选功能

战略重要性和使用强制性是两个维度。用户不开启 LifeModel 也应该能正常完成任务；开启时应得到清楚、可验证的增益。当前默认关闭和近期冻结深度开发，是基础产品尚需可靠性验证的阶段安排，不是降低它在长期产品中的地位。

既有合同：来源 → 原子 Proposal → 用户编辑/批准 → 正式 LifeModel → 选择与预览 → 官方上下文入口；不允许 Runtime 自动写正式内容。

## 04 用一个连续工作场景说明 LifeModel

以下是目标体验示例；不是当前产品全部已完成的演示

| 时点                           | 用户与 Agent 的工作                                            | LifeModel 在其中做什么                                     |
| ------------------------------ | -------------------------------------------------------------- | ---------------------------------------------------------- |
| 第一天：用 Pi 做报告           | 用户明确说：项目汇报先讲目标和结果，再讲技术；区分事实与建议。 | 从真实用户陈述形成候选，用户可编辑其范围并批准。           |
| 第二周：换 OpenCode 做项目材料 | 在新的原生 Session 开始另一项工作。                            | 用户选择相关偏好，发送前看到将使用的内容与来源。           |
| 之后：另一 Agent 做复核        | 通过明确的交接材料检查产物；它不继承前一个 Agent 的隐藏状态。  | 只共享与复核有关的已批准约束；交接材料独立存在。           |
| 用户改变习惯                   | 用户决定某类汇报改为面向非技术读者。                           | 更新形成提案；冲突经明确决策后处理，旧值不会静默覆盖新值。 |

### 完整价值链

不是“记住一句话”就结束。系统需要记得准确、知道何时适用、在对的任务使用、对结果产生帮助，并允许用户修改或撤回。跨 Runtime 共享不意味着每个 Agent 都看全部信息；来源来自哪个 Agent，也不决定这条理解归谁所有。

### 现在已有与仍需建设

已有的治理原型覆盖来源、提案、用户批准、正式条目以及注入记录，历史 QA 验证过双来源、冲突、撤回和删除。下一步要解决的是候选质量、作用范围、时效、相关性选择和低负担的人机交互；长期还要证明它改善真实任务。当前不具备自动构建完整人生画像或持续自我学习的成品证据。

撤回或删除会阻止 Farfold 后续按相应规则使用内容；已经发送给 Runtime 或 Provider 的信息可能留在对方原生历史中。不能把删除 LifeModel 描述为从所有外部系统追溯擦除。

场景为说明性设想；实现与边界依据 PRODUCT.md、lifemodel.rs 和 D4 原生验收记录。

## 05 长期产品结构：围绕用户组织能力

## 08 短期目标：让团队真正依赖它工作

当前处于 S1 后段：单机安装交付已有，团队使用闭环待补

短期最重要的结果是：成员不需要开发者在旁边，能够用自己的账号完成真实工作，并在失败、退出和升级后知道如何继续。0.1.6 的工程交付为这一目标打下基础，但不能代替真实使用接受。

| 工作重点         | 应形成的成果                                              | 建议验收方式                                      |
| ---------------- | --------------------------------------------------------- | ------------------------------------------------- |
| 独立安装与认证   | 第二成员从安装到自己的首次成功任务。                      | 自己的机器与账号；记录所需帮助和耗时。            |
| 成果质量闭环     | 代码、页面、文档按实际用途被接受。                        | 打开产物、运行必要检查；不以 Agent 自报完成统计。 |
| 服务失败可理解   | 区分 Host、Runtime、模型、权限、余额与网络故障。          | 保留原始原因，验证下一步操作能否帮助恢复。        |
| 连续性与目录安全 | 停止、重启、草稿和原生 Session 连续；不同工作范围不混写。 | 真实日用任务加已有负面验收，记录异常。            |
| 升级与用户数据   | 安装物、数据与恢复路径配套。                              | 沿用当前手动配对恢复，后续更新另行验收。          |

### 建议的最小观察窗口

在团队认可后，用连续两个工作周、至少两位独立使用者、覆盖代码与文档的真实任务记录建立基线。它只是低成本观察方案，不是统计充分性或当前已达成指标。严重误目录写入、未经确认的信息注入、有副作用自动重放应作为停止扩面的条件。

此阶段 LifeModel 保留入口、可选与审批语义，深度产品开发继续等待基础可靠性。研究可以先明确效果评价方法，避免恢复开发时只继续堆功能。

当前事实来自 PRODUCT.md、INTERNAL-USE.md 与 active plan；观察窗口与退出条件是本报告建议。

## 09 中期目标之一：从双 Runtime 到广泛覆盖

扩展目标是满足选择自由，技术策略是按接入面复用

“尽可能把能接的都接进来”适合作为生态方向，但产品支持范围需要有清楚分母：有可使用的正式接口、能在目标环境运行、能保留原生会话和关键控制、版本及认证可维护的候选。只有模型 API 的服务、开发框架库、GUI-only 应用和远程 Agent 服务需要分开评估。

| 接入路径               | 建议采用方式                                          | 为什么                                                   |
| ---------------------- | ----------------------------------------------------- | -------------------------------------------------------- |
| Pi / OpenCode          | 保持已验证 JSONL RPC 与 HTTP/SSE Adapter。            | 保留原生能力与回归证据，避免为了统一协议先重写稳定链路。 |
| 成熟 ACP 候选          | 增加共享 ACP client，并保留按候选划分的能力与扩展。   | 复用会话、流式更新、权限等公共协议，降低重复工程。       |
| 有更完整官方接口的候选 | 比较原生 SDK/App Server 和 ACP 包装器，再选择主路径。 | 完整性、恢复和版本维护比“都说一种协议”更重要。           |
| 无可用官方控制面       | 记录暂不支持及缺少的能力。                            | 不通过嵌入原生 UI、逆向私有接口或修改 Runtime 凑数。     |

建议先选一个有代表性的 ACP Runtime 和一个原生接口候选做新协议校准，随后扩展到高频名单。共享代码的验收通过，不能替代每个 Runtime 的安装、登录、真实工具任务、权限、停止和恢复验收。

每个候选显示“基础工作 / 贡献 LifeModel / 使用 LifeModel”三个独立状态。一个 Runtime 可以先只支持基础工作；不能因为 ACP 能发 prompt 就标记完整 LifeModel 支持。

技术建议依据现有 Adapter 边界及 [ACP 协议概览](https://agentclientprotocol.com/protocol/v1/overview)、[ACP Registry](https://agentclientprotocol.com/get-started/registry)。

## 10 中期目标之二：证明 LifeModel 有用

从“数据能治理”走向“个人理解能改善任务”

已有原型回答的是内容怎样可信地进入和被使用。下一阶段更关键的问题是：哪些内容值得留下，何时应该使用，错误或过时理解怎样纠正，以及用户愿不愿意持续维护它。不能用条目数量、Proposal 数量或注入次数替代效果。

| 建设方向   | 建议先做的窄切片                                         | 需要观察什么                             |
| ---------- | -------------------------------------------------------- | ---------------------------------------- |
| 候选准确性 | 稳定工作偏好与明确约束；保持来源可追溯。                 | 错提议、遗漏、秘密和第三方内容误入。     |
| 范围与时效 | 区分全局/特定项目适用；支持变化和冲突决策。              | 旧偏好是否错误压过当前指令；跨项目串用。 |
| 相关性使用 | 少量、任务相关、发送前可看可移除的内容。                 | 重复解释是否减少；无关干扰和额外成本。   |
| 维护负担   | 可理解的提案、编辑与撤回体验。                           | 用户花多少时间确认；是否因烦琐而放弃。   |
| 效果验证   | 同一任务类型比较关闭、人工带上下文、LifeModel 三种条件。 | 接受率、返工、用时、用户信任和成本。     |

### 研究与产品如何衔接

LifeModel 效果研究由独立研究工作承担，向产品提供失败类型、评测方法与可复用结论。产品负责原生来源、注入、用户控制和真实体验。研究结果进入产品前还要做同一安装版本验收；研究材料不直接成为产品合同。

建议从两种 Runtime 和一个稳定场景验证净收益；没有必要等覆盖全部 Runtime。若尚无收益，应缩小内容范围、调整使用方式，或继续保留可选试验状态，不能把“核心战略”当作有效性的替代证据。

本页为 S3 建议。既有 C1/U1 和 D4 验证证明接口及治理可行，未证明长期个性化效果；当前深度开发冻结仍有效。

## 11 中远期目标：让不同 Agent 真正协作

并列运行、上下文交接和委派合作是三种不同能力

![图 3 · 建议的首个协作结构：用户或已选 Runtime 发起明确委派，Farfold 管理任务关联与边界，各 Runtime 保留自己的 Agent loop。](/Users/tw/Desktop/farfold/reports/2026-09-07-project-status/assets/collaboration.svg)

| 层次                 | 用户体验                                                | 建设边界                                      |
| -------------------- | ------------------------------------------------------- | --------------------------------------------- |
| 当前：并列使用       | Pi 与 OpenCode 各自在自己的会话中做事。                 | 已有受限并发；不等于双方交换成果。            |
| 下一步候选：显式交接 | 用户选择目标、摘要和产物，在另一 Runtime 的新会话继续。 | 不伪装原生 Session 迁移；展示交接内容。       |
| 随后候选：有界委派   | 一个 Runtime 做主任务，另一个承担明确子任务或复核。     | 有任务关联、范围、费用/并发限制、取消与恢复。 |
| 更远期：长期协作     | 跨时间、服务或设备的 Agent 围绕目标持续配合。           | 需要独立验证长期状态、授权、远程边界。        |

建议从“一个实现、另一个只读复核”开始，比较单 Agent 的结果与总成本。避免首个版本就让多个 Agent 同时改同一份文件；独立工作副本或串行交接需要先明确。LifeModel 只提供相关个人约束，任务输入、依赖与产物另行传递。

Farfold 可以管理明确任务的传递与运行状态；自主拆解和工具决策仍由所选 Runtime 负责。若未来要由 Farfold 自己成为中央规划 Agent，那是另一项产品边界决策，当前路线没有默认批准。

方向依据本次用户要求；MCP 委派模式可参考 [Codeg 协作机制](https://docs.codeg.app/guide/multi-agent)；不是 Farfold 当前已实现能力。

## 12 长期方向：从一次交互到持续服务

让长期用户理解转化为长期帮助，同时保留退出与纠正能力

长期理想是：用户的目标、习惯与明确约束能够在多个项目和时间段中持续帮助工作。Farfold 可以逐步支持目标跟进、定期准备材料、发现需用户决定的事项，并组织合适的 Agent 完成受授权的任务。这里的“理解”应持续可纠正，不把用户冻结成一个永远不变的画像。

| 可能演进             | 带来的价值                                 | 进入前提                                     |
| -------------------- | ------------------------------------------ | -------------------------------------------- |
| 受控触发与主动提示   | 无需每次重新开口，重要进展可及时到达用户。 | 触发范围、通知频率、失败和取消边界清晰。     |
| 持续的项目与目标工作 | 跨天、跨周工作可以追踪成果并恢复。         | 持久任务状态、预算、幂等和中断恢复已验证。   |
| 更丰富的个人理解     | 偏好与长期目标共同帮助决策和执行。         | 效果研究支持；敏感范围、时效和更正体验可靠。 |
| 可选远程与多设备     | 工作在合适的设备执行，人可从其他入口接续。 | 身份、加密、同步冲突、权限和数据流明确。     |
| 专业 Agent 服务协作  | 与外部专门服务完成更复杂目标。             | 服务确有正式接口；A2A 等协议和授权逐项核验。 |

这些方向都没有当前交付承诺。主动服务也不等于自行替用户作出重要决定；普通执行权限继续由 Runtime 承担，长期个人理解的更新继续由用户掌控。多设备、云同步或实体设备不是使命成立的前置条件。

### 长期判断标准

不是系统记住了多少内容、接了多少 Agent，而是用户是否更少重复解释、更少人工协调、更稳定地完成重要工作，并能理解和纠正系统行为。

本页为愿景与可能路线。A2A 的定位参考 [A2A 官方介绍](https://a2a-protocol.org/latest/topics/what-is-a2a/)；协议存在不表示外部服务已可直接接入。

## 14 商业路线：为持续价值收费的前提是什么

建议先验证选择理由，再决定收费和分发

Farfold 的商业假设是：当用户在不同 Agent 间长期工作时，会愿意为可靠工作台、可控的个人理解与更少人工协调付出成本。当前没有证据证明该假设成立；内部版本不是商业化完成状态，也没有经核实的收入、获客成本或市场规模。

| 可选模式            | 用户可能为什么付费                               | 主要约束                                                |
| ------------------- | ------------------------------------------------ | ------------------------------------------------------- |
| 个人软件许可 / 订阅 | 长期维护、可靠升级、好的工作体验与个人理解服务。 | 必须证明相对免费方案的持续收益；具体模式和价格待验证。  |
| 团队管理与支持      | 可部署、可恢复、支持响应、共享项目流程。         | 个人 LifeModel 与团队资料分开；目前未实现企业管理产品。 |
| 可选托管 / 同步服务 | 省去机器维护，获得可接续的远程执行。             | 基础设施成本、远程权限和数据承诺增加；不应提前捆绑。    |
| 生态赞助 / 服务合作 | 发行、维护或特定服务带来合作机会。               | 商业关系不能损害 Runtime 选择中立与用户信任。           |

### 现成的商业参照

Zed 的公开页面显示 Personal 免费，Pro 为每月 10 美元，Business 为每席每月 30 美元；收费价值包括托管 AI 和组织管理，而外部 Agent 可自带认证。这说明工作台费用与 Runtime/模型费用可以分开；不意味着 Farfold 应直接照搬定价。 [Zed 定价](https://zed.dev/pricing)

### 建议的验证顺序

先从内部任务找出高频痛点，再邀请少量目标用户携带自己的真实任务试用；比较原工作方式、一个合适的现成工作台和 Farfold。记录首次成功、重复使用、人工帮助及愿意保留/付费的具体理由，再设计商业试验。

成本应分别记录：宿主维护与支持、每个 Adapter 的版本回归、模型/Runtime 使用费、后续远程服务成本。BYOK 意味着模型费用通常由用户另付，不意味着使用免费；也不能默认某家订阅能给任意第三方宿主使用。

本页商业模式为建议。价格为查阅日公开值；外部 Runtime 的具体认证、分发与服务条件在接入时逐项核验。

## 15 技术对比：共同模式与不同选择

商业外观相似，内部责任与维护成本未必相同

| 产品          | 接入与宿主技术                                                                                                  | 我们可以学习 / 需要区别                                                              |
| ------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Codeg         | Rust 共享核心 + Tauri / HTTP、WebSocket；主要以 ACP 接入，MCP companion 提供委派。                              | 学习 ACP 公共层、安装健康检查、异步委派；不直接复制各家私有历史解析。[W01–W04]       |
| Verde         | Zig + SDL3/Palette + SQLite；Pi RPC、OpenCode serve、Codex App Server、Claude SDK 与 ACP 混用；Session daemon。 | 接入哲学接近；后台连续性值得参考。Farfold 保持自有 UI，不嵌入 Runtime TUI。[W05–W06] |
| Harnss        | Electron/React；Claude Agent SDK、Codex 和 ACP；依赖中有 ACP SDK、MCP SDK。                                     | 学习工具卡片与差异化能力呈现；其重写计划提示不能直接拿早期架构作稳定基础。[W07–W08]  |
| Agent Cockpit | 本地 Web + CLI Adapter；Kiro ACP、Codex App Server、OpenCode JSON CLI；Markdown 上下文。                        | 能力矩阵明确差异；共享 Markdown 可便携，但不是 Farfold 的逐条审批写入链。[W09–W10]   |

因此没有必要为了显得不同而重造 ACP、RPC 或桌面框架。真正需要自主掌握的是责任划分、原生连续性、能力差异的呈现、用户数据语义与实际成果体验。使用共同协议，仍然可以做出不同产品。

参考对象 20x 更偏任务与工单编排，公开架构使用 Electron、SQLite，以及 OpenCode/Claude SDK、Codex ACP。可观察任务接入与流程组织，但它与“个人 LifeModel 为中心”的产品并非完全同类。 [W15]

技术结论来自官方架构文档、README 与依赖清单；没有本轮完整审计第三方所有源码，也不把宣称的性能与安全当作独立验证。

## 16 把 ACP、MCP、A2A 讲明白

三个协议解决不同的连接问题；它们不会自动带来个人理解

![图 4 · 连接位置：ACP 常用于工作台与 Agent；MCP 用于 Agent 与工具/上下文；A2A 可用于外部 Agent 服务之间的协作。](/Users/tw/Desktop/farfold/reports/2026-09-07-project-status/assets/protocols.svg)

| 技术                | 大白话解释                                                            | Farfold 建议用法                                                    |
| ------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------- |
| ACP                 | 工作台和 Agent 的共同对话规则：建会话、发任务、收进度、转权限、取消。 | 中期扩展接入的共同层；保留各 Runtime 原生能力与扩展。               |
| MCP                 | Agent 访问工具和资料的统一接口，也可暴露有限委派工具。                | 适用时作为受限上下文或委派入口；不能暴露全量 LifeModel 的任意读写。 |
| A2A                 | 独立 Agent 服务之间交流任务、状态和产物的协议。                       | 有真实远程/跨框架服务需求时再评估；当前本地接入不依赖它。           |
| 原生 SDK/RPC/Server | 某个 Runtime 提供的正式控制接口，通常更贴近它自己的能力。             | 保留 Pi/OpenCode；候选按完整性与维护成本选择。                      |

ACP 通常用 JSON-RPC 双向交换消息；本地连接可走标准输入输出。initialize 协商能力，session/new 创建，session/prompt 发送，session/update 回传，session/cancel 取消。session/load 是可选能力：接上 ACP 不等于恢复、工具呈现和所有交互都已支持。

若 Agent 请求 ACP 的文件或终端能力，Host 可能需要实现受限的本地服务。它是执行明确协议请求，不是自行决定工具或重写 Agent loop；必须单独核对权限与目录边界。

来源：[ACP 架构](https://agentclientprotocol.com/get-started/architecture)、[协议概览](https://agentclientprotocol.com/protocol/v1/overview)、[MCP 官方介绍](https://modelcontextprotocol.io/docs/2026-07-28/getting-started/intro)、[A2A 官方介绍](https://a2a-protocol.org/latest/topics/what-is-a2a/)。

## 17 建议技术路线：原生深接入 + ACP 扩面

不要把注册表名单、历史 PoC 和产品支持混为一谈

| 候选 / 当前状态         | 建议主路径                                      | 进入下一阶段前验证                                                |
| ----------------------- | ----------------------------------------------- | ----------------------------------------------------------------- |
| Pi / 已安装验收         | 保留官方 JSONL RPC 和现有能力桥。               | 持续原生回归；不因存在 pi ACP 包装器就替换。                      |
| OpenCode / 已安装验收   | 保留官方 HTTP/SSE；ACP 作为比较面。             | 已知能力在版本升级后仍成立，配置与原生恢复正确。                  |
| Codex / 历史独立 PoC    | 优先评估官方 App Server；与 ACP Adapter 比较。  | 新固定版本的认证、Thread/Turn、审批、恢复、原生功能。             |
| Claude Agent / 尚未接入 | 比较官方 Agent SDK 与维护良好的 ACP wrapper。   | SDK 仍运行上游 loop；核对配置、Session、权限与实际可用认证。      |
| Kimi / 历史独立 ACP PoC | 可与 Gemini、Qwen 等候选比较后选 ACP 校准对象。 | 当前固定版本、Provider 可用性、恢复、权限、来源及上下文通道。     |
| 其他 Registry 候选      | 需求驱动纳入 ACP 接入队列。                     | 辨别厂商原生协议和第三方 wrapper；固定包装层与 Runtime 两种版本。 |

建议顺序是：先闭环 S1 → 选代表候选更新接口 PoC → 完成第一个 ACP 安装切片 → 以第二个 ACP 候选检验可复用性 → 按用户需求扩面。Codex 等原生候选可按真实需求排入，不凭品牌或注册表排序自动决定优先级。

本轮官方 Registry 将 pi ACP 标为 adapter；Codeg 的支持页对若干包装关系用了更宽泛的表述。因此报告采用保守分类：名称相同不代表同一分发物，也不代表当前 Farfold 的 Pi 路径已具备 ACP。旧 PoC 的版本不能作为今日兼容性保证。

来源：[Codex App Server](https://learn.chatgpt.com/zh-Hant/docs/app-server)、[Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview)、[OpenCode ACP](https://opencode.ai/docs/acp/)、[ACP Registry](https://agentclientprotocol.com/get-started/registry)；历史 PoC 见 research/2026-08-30。

## 18 技术重心与复用策略

借鉴成熟模式，把精力用在能够产生用户价值的层面

## 27 总体架构：谁负责哪一层

源码追踪后的系统图

![图 11 · 实线为现有基础工作链，右侧为 Farfold 自有持久化。](/Users/tw/Desktop/farfold/reports/2026-09-07-project-status/assets/architecture.svg)

前端是 React 19、TypeScript 5.9 与 Vite 8；桌面宿主为 Tauri 2，使用 Rust 管理进程、IPC、存储与安全边界。它是模块化的本地 Host，没有部署一组微服务，也没有自研替代模型或 Agent Loop。

HostSessionController 约束新建、打开、停止及维护；TurnCoordinator 决定一个 Turn 是否允许进入，并保留会话、目录与 Runtime generation 的绑定。RuntimeSupervisor、事件路由、交互注册和会话协调分别处理连接状态、事件分发、待回复交互与恢复。

Pi 走官方 JSONL RPC；Provider 能力由固定版本的独立 capability bridge 提供。OpenCode 由 Host 启动本地受认证 HTTP Server，并通过 HTTP 命令与 SSE 事件通信。共同 UI 只统一呈现，不把两路所有原生事件压成同一种行为。

> 这套架构的价值是把“换一个 Agent 引擎”限制在可审查的适配层；它降低接入耦合，但每新增 Runtime 仍要做协议、权限、原生连续性和安装验收，不能承诺即插即用。

依据：[S05–S09] lib.rs、runtime_host、session_controller、turn_coordinator、事件路由与两路 Adapter。

## 28 一条任务如何真正执行

从点击发送到完成／恢复的控制链

![图 12 · Host 控制准入与身份，Runtime 执行 Agent 循环，UI 呈现真实结果。](/Users/tw/Desktop/farfold/reports/2026-09-07-project-status/assets/turn.svg)

| 步骤           | 关键动作                                                          | 为什么需要                                   |
| -------------- | ----------------------------------------------------------------- | -------------------------------------------- |
| 1 选择会话     | 绑定 Runtime 产品、安装、构建、连接、项目、工作副本和原生 Session | 避免切换界面后把指令送到错误历史或目录       |
| 2 Host 准入    | 检查维护状态、同会话忙碌、同 Working Copy 占用和总活动数          | 避免并发踩踏；上限为 2                       |
| 3 Adapter 提交 | Pi 等待关联 response；OpenCode 使用原生 Session 提交              | 写入管道不等于 Runtime 已接受                |
| 4 事件回传     | 带来源身份、序号、generation、原始 envelope                       | 过滤过期流、识别缺口，不把旧输出混入新会话   |

## 29 数据架构与身份绑定

Host 保存目录，Runtime 保存工作原件

![图 13 · 会话身份与数据归属；切 Runtime 是另一会话，不是搬运不透明状态。](/Users/tw/Desktop/farfold/reports/2026-09-07-project-status/assets/data.svg)

| 数据                       | 实际归属与保存方式                                           | 风险边界                                           |
| -------------------------- | ------------------------------------------------------------ | -------------------------------------------------- |
| 导航／项目／会话引用／草稿 | Farfold SQLite，当前 schema 7；有约束、事务、WAL、完整性检查 | 数据损坏／未知未来 schema 进入恢复边界，不继续盲写 |
| Pi 原生历史                | Farfold profile 内的 Pi Session JSONL；Host 保存准确定位     | Host 记录删除不等于原生历史删除                    |
| Pi 必要配置                | 默认共享 ~/.pi/agent；支持明确目录覆盖                       | 开发／日用 Host 隔离不等于所有上游配置隔离         |
| OpenCode 原生状态／认证    | Farfold profile 下隔离的 config/data/cache/state             | 不等于共享 CLI 的登录状态                          |
| 项目文件与 Git             | 实际用户目录和工作副本                                       | 不在 Host 可移植备份中                             |
| LifeModel                  | SQLite 内版本化 JSON 文档与 revision                         | 来源、提案、正式条目、注入清单分别保留语义         |

身份不是只有一个 runtime_id：同一 Runtime 产品可能有不同安装、版本和连接；同一项目也可能有多个实际工作目录。源码用独立类型、外键与绑定校验把这些关系拆开。这样做增加了实现量，但减少“恢复错会话、运行错目录”的隐蔽风险。
