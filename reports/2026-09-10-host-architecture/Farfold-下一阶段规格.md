## 1. 产品目标

用户通过 Farfold 使用 Pi、OpenCode、Codex 时，应尽量保留对应 Agent 原生工作的必要能力：
真实项目、真实模型、原生工具、权限 / 提问、停止、恢复和成果审阅。验收比较的是同一 Agent、
固定版本、同一项目、同一配置和等价输入下的工作流程与能力覆盖；不要求随机模型输出逐字一致。

本阶段只覆盖 Pi、OpenCode、Codex。第四个 Agent、跨 Agent 协作、远程 Host、LifeModel 深度集成、
账号池和商业分发不进入本规格。

## 2. 分层职责

Farfold 工作台负责统一的项目、会话、输入、状态、交互、文件成果和错误出口。它显示 Runtime
身份和能力差异，但不嵌入或仿制第三方 UI。

Host 负责项目 / Working Copy / 安装 / 连接 / 原生会话 / 任务 / 请求的唯一身份，持有自己启动的
进程，执行两条活动任务和同 Working Copy 排他限制，保留原始事件和未知状态。

公共 ACP 客户端负责协议连接、握手、能力协商、事件订阅、取消和请求回复。一套实现可以服务多个
连接实例；适配器内部调用原生 SDK、RPC 或 Server 不等于 Farfold 重新保留多条旁路控制权。

安装管理优先选择用户本机已有 Agent；缺失时再提供按需安装。每个安装引用记录 Agent、适配器、
依赖版本、路径、摘要、启动方式和验证时间。Farfold 不偷偷升级用户全局程序。

Provider 管理保存 Farfold 自己管理的连接、端点、地区 / 套餐、凭据引用和模型映射，并逐目标投影
到兼容 Agent 支持的配置方式。模型调用仍由 Agent 发出；已配置、已应用、已验证请求和失败原因分开。

## 4. 正常流程

新建任务时，用户选择 Project / Working Copy、Runtime、安装引用、连接和模型。Host 创建原生会话并
持久化身份后才发送首条任务。发送成功只说明 Runtime 接收了请求；任务完成必须来自原生终态、实际
文件和 UI 投影的交叉核对。

继续任务时，Host 先核对安装、连接、Project、Working Copy 和原生会话引用。原生记录缺失、版本不兼容
或配置未就绪时保留绑定、标题和草稿，并给出恢复动作。

运行中，Farfold 显示启动中、执行中、等待用户、停止中、完成、失败或结果未知。权限、提问和停止请求
由原生 Agent 发起或确认；Farfold 不自动批准、不自动补发、不把普通聊天伪装成原生提问。

## 5. 失败行为

发送后断线或响应丢失时，显示状态待确认，先查询原生状态。没有证据时保留占用和草稿，不自动重发。

等待交互时切换会话、取消或过期后，旧按钮失效。迟到回复不能落到另一会话或新连接代次。

Provider 修改只在对应目标安全边界生效。活动任务继续使用开始时绑定的连接和模型；部分投影失败不显示为
全部成功。

外部编辑器与 Agent 同时改文件时，Farfold 只说明观察到的文件差异和比较基线，不把全部磁盘变化归给 Agent。

升级或用户移动程序时，保留旧可用安装和会话绑定，要求重新定位 / 校验启动引用；不静默改绑另一个构建。

## 6. 验收

每个开发切片都要区分源码 / 自动测试 / 原生对照 / 安装应用 / 用户验收。安装应用验收至少覆盖真实配置、
文件任务、权限或提问、停止、断线不重发、冷启动续接、配置隔离、成果定位和基础窗口可达性。

三路最终验收必须在同一候选应用中核对固定 Agent / 适配器 / 程序摘要、Provider 请求、原生会话 ID、
实际工作目录、真实产物、冷启动恢复、并发限制和配对恢复。未知、官方限制和未实现项单列，不用握手成功或
单元测试替代产品可用性。

### 附录 3 阶段顺序与退出条件

1. **阶段 A：冻结证据、三路能力输入与工作区边界。**
   开始条件：用户已批准本计划；核对当前工作区与 QA 进程状态。
   工作内容：核对当前改动归属、敏感文件排除、唯一活动计划和报告引用；盘点已有三路 ACP / Host 研究结论，
   将每条标为仍有效、版本过时或证据缺失；只补必要缺口并更新原有权威位置。Codex 候选组合、
   Pi ACP 能力损失和 OpenCode 固定版本差异都在 A 给出证据状态，不拖到后续才首次核查。
   退出条件：明确哪些变更属于已授权取消/ACP包、哪些是待审阅额外变更；三路能力输入足以定义公共边界；
   不提交、不清理未归属文件。

2. **阶段 B：公共 Host / ACP 边界收口。**
   工作内容：基于三路需求修正 turn/operation/generation/connection 的统一合同；区分 accepted、
   confirmed cancelled、unknown、not sent；补旧 generation、迟到 ack、verify 失败、pending permission 清理测试。
   明确原生提问、权限、Host 文件/Git/diff、Host 终端能力、Agent 工具执行边界和专属扩展的公共接口。
   退出条件：源码测试证明旧回执不能影响新 turn；断线/超时仍 unknown；confirmed cancel 释放 admission；
   同 working copy 可开下一轮；公共接口能解释 Pi、OpenCode、Codex 三路差异。此阶段不声称 installed 通过。

3. **阶段 C：OpenCode 第一顺序的完整纵向流程，按小切片审阅。**
   工作内容：以 OpenCode 跑通前端 → Host → 公共 ACP → Agent 的 Farfold 完整流程。每个切片都要说明
   输入、主要代码边界/复用点、用户行为、异常验收、删旧时点和回退点；不先做抽象大全，也不把公共基础推迟到
   Pi/Codex 后。参考 [Google small CL](https://google.github.io/eng-practices/review/developer/small-cls.html)
   原则：小变更应自包含、带相关测试、便于审阅和回退；这里只采用工程节奏依据，不引入外部机器治理。

   - C1 安装引用与连接启动：输入为阶段 A 的 OpenCode 固定版本/来源结论；边界在 Host 安装、discovery、launch
     和 ACP connection；用户行为是选择本机程序或缺失时按需安装/修复；异常验收覆盖多版本、缺失、摘要不符、
     启动失败和失败进程清理；此切片做针对性检查和连接冒烟，旧入口在 C 阶段安装应用验收后删除。
   - C2 Provider 与任务绑定：输入为统一 Provider 连接和投影规则；边界在 Host Provider、turn coordinator 和
     Adapter 原生配置应用；用户行为是一次保存、应用到 OpenCode、开始任务；异常验收覆盖保存成功但应用失败、
     请求验证失败、活动任务改配置、错误目标回执；凭据不输出。
   - C3 任务/交互/取消：输入为 ACP prompt、permission、question、cancel 能力矩阵；边界在公共 ACP、InteractionRegistry、
     工作台交互组件；用户行为是发送、等待权限/提问、允许/拒绝/取消/停止；异常验收覆盖旧请求、密文、重复回复、
     断线、进程退出、重启不重发。
   - C4 文件、Git、终端与 coding 体验：输入为 ACP 工具事件和 Host 文件/终端合同；边界在 Host 文件/Git/diff/终端服务、
     ACP 回调和公共工作台；用户行为是查看代码块、文件定位、工具过程、终端输出、产物审阅；异常验收覆盖路径越界、
     符号链接、外部编辑、非 Git、二进制/大文件、冲突、终端输出上限和退出清理。Host 提供真实资源，Agent 仍拥有工具决策和执行语义。
   - C5 会话恢复与入口收敛：输入为原生 session/load、Farfold 会话绑定和 installed app 状态；边界在 Host 会话、
     recovery、sidebar 和工作台入口；用户行为是冷启动恢复、继续任务、从侧栏返回；异常验收覆盖打不开不新建空会话、
     取消中退出重开、重复启动 ACP、旧入口状态漂移。C 阶段集中验收通过后再删被替代的实验/旧控制入口，并检查删除影响。

   退出条件：同一候选安装应用、固定真实 OpenCode Agent、同一 managed connection、真实受支持 Provider 下完成 C1-C5；
   本地 fixture 只用于可控故障和协议验证，不能替代完整端到端证据。Reject 必须核实工具未执行或原生拒绝语义，
   不能只看没有后续模型请求。手工 kill 只可作为失败收束，不算产品成功。

4. **阶段 D：Pi 第二顺序接入与复用验证。**
   工作内容：以阶段 B/C 的同一公共 Host、ACP、工作台接口接 Pi；复用 Provider 连接版本、安装引用、
   文件/终端/审阅服务和恢复合同；只把 Pi 专属 steer/follow_up/Extension 差异保留在 Adapter。
   退出条件：Pi 不静默降级已有专属交互；若 ACP adapter 不能保留能力，明确阻塞或保留原生路径；
   发现公共缺陷回到公共实现修正，不复制 Pi 专用控制体系。Pi 原生旧路若临时保留，只能标为未迁移状态，
   不能算 ACP 目标完成。

   2026-09-13 用户已明确批准第二种模型/认证结构方案并要求实施：复用同一公共 Host/ACP 和
   现有 Pi Adapter，官方 SDK 在 Adapter 内辅助认证/目录，Pi 进程继续执行 Agent；稳定自有
   profile/启动引用与每轮 managed-version/native-observation 来源分离。实现必须明确多版本
   投影及凭据冲突、模型选择至 turn admission 的原子捕获、认证取消与秘密边界、既有 managed
   Session 沿唯一原身份恢复。禁止 SDK 接管 Agent、Host RPC 旁路、伪造 key、放松模型校验或
   把 native 观察记作 managed VerifiedSuccess。必要 schema 变更按保护与分层验收规则执行；
   能否同进程刷新需固定 Pi 证据，必须重启则明示并恢复原 Session，不重放任务。此项不再待批准。

5. **阶段 E：Codex 第三顺序接入与复用验证。**
   工作内容：执行阶段 A 已标定的 Codex ACP SDK、adapter、Agent 组合验证；复用同一公共 Host、ACP、工作台、Provider、
   安装引用、文件/终端/审阅和恢复合同；保留已接受的 App Server / 原生提问 / 冷历史限制。
   退出条件：Codex 支持项、官方限制和未实现项均有固定版本证据；发现公共缺陷回到公共实现修正；
   不把 0.143.0 App Server 证据外推到未验证 adapter 组合。

6. **阶段 F：三路安装复用验证与去随包。**
   工作内容：复验三路本机优先安装引用、所选程序、按需安装、下载校验、失败回退、移动/升级重定位；
   在 C 已完成 OpenCode 基础安装流程后，把同一 Host 安装服务用于 Pi/Codex 并逐步移除 Pi/OpenCode 过渡随包资源。
   退出条件：主包无 Agent 本体仍可首次启动；三路缺失/多版本/移动/升级都有恢复出口；重要 Provider 配置、新阶段会话和需保护的日用数据可恢复。
   不迁移已明确可舍弃的旧开发会话，不据此删除新日用数据或外部 Runtime 历史。

7. **阶段 G：三路同候选应用验收与收尾。**
   工作内容：同一候选应用串联三路新建、任务、交互、停止、恢复、Provider、成果审阅、并发、配对恢复。
   退出条件：安装应用证据、自动检查、原生对照、用户验收分层记录；Pi timeout 等未知仍单列；替代路径按清单删除。

### 附录 4 为什么按此顺序

- 先收 Host 生命周期，是为了阻止多入口继续各自判断“当前任务是否结束”。没有这一层，ACP、Provider、安装都会继续新增
  boolean 和局部回调，问题会扩散到 Pi/Codex。
- 三路能力核查前置，是为了让公共 Host/ACP 先知道 Pi 的 steer/follow_up/Extension、OpenCode 的 permission/cancel、
  Codex 的 question/interrupt 和文件/终端边界；首路实现不能只按 OpenCode 特性塑形。
- OpenCode 作为第一接入顺序，是因为已有真实 permission surface、fixed 1.18.30、managed Provider 和 session/load
  纵切证据；但它的目标是完整 Farfold 纵向流程，不是单独完成 OpenCode 客户端。
- Pi 第二、Codex 第三。每接一路都同时验收公共 Host、ACP 和工作台是否真实复用；首路通过只证明首路完整，
  不证明通用完成。
- Provider 和安装可以独立规划，但实施时必须消费同一 Host 身份和配置版本合同。Provider 解决“任务用哪个配置”，
  安装解决“运行哪个程序/adapter”，两者在 OpenCode 首路共同接通；二者不能合成一个 `runtime_id`。
- 后续发现共性缺陷必须回到公共实现修正；必要专属差异保留在 Adapter，不能复制另一套控制体系。
- 删除旧路径必须跟在 installed 验收之后，防止为了“统一”删掉 Pi/Codex 已接受能力。

### 附录 5 验收证据分层

| 证据层                      | 能证明什么                             | 不能证明什么                                   |
| --------------------------- | -------------------------------------- | ---------------------------------------------- |
| 源码/官方文档               | 接口存在、协议语义、固定版本限制       | 产品已可用、真实 Agent 已按预期执行            |
| 单元/集成测试               | Host 合同、边界条件、时序和旧回执处理  | 安装应用 UI、系统权限、真实用户流程            |
| 固定 Agent + 本地 fixture   | 可控故障、协议分支和 Host 回调合同可测 | 真实 Agent 端到端、真实 Provider、产品替换完成 |
| QA Shared installed visible | 同一候选包的桌面流程可达               | 正式应用已升级、所有机器可用                   |
| 正式日用安装                | 当前用户本机日用路径可用               | 团队其他机器或未来版本自动可用                 |

完整替换的共同门槛：阶段 A 确定的已接受能力，必须在对应 Agent 的替换验收中逐项通过；
“已确认缺口”不算完成，必需能力缺失时不得删除旧可用路径或宣布该路迁移完成。
Agent 未使用的文件/终端回调可通过协议合同测试验证公共服务，但需单列“未验证该 Agent 实际调用”，
不得为验收要求 Agent 改用它原本不用的工具路径。公共键盘操作、焦点、可读错误与无障碍交互纳入 C 的界面验收。
首路通过后，Pi/Codex 接入仍需实际验证同一套服务的复用，不能以 OpenCode 结果代替。

### 附录 5a 测试节奏与成本控制（用户已批准）

原则：日常针对性小检查、流程接通后简短验证、阶段出口集中完整验收。小切片是实现和审阅单位，
不等于每片都重打安装包、调用真实模型或执行整套测试。保留发现错误的及时性，减少无变化的重复验证。

| 时机                                 | 必须做                                                                                              | 不默认重复做                             |
| ------------------------------------ | --------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 日常改动                             | 检查受影响的类型、逻辑和相关行为测试；取消、配置绑定、旧代次隔离、数据保护等关键规则修改后及时验证  | 无关测试、全量构建、安装包、真实模型调用 |
| 一条流程接通                         | 简短集成/冒烟，确认前端、Host、ACP、Agent 的实际连接；优先复用开发环境与可控测试条件                | 每完成 C1–C5 中一步就完整桌面回归        |
| C、D、E 阶段出口与最终交付           | 固定真实 Agent、真实受支持 Provider、同一候选安装应用集中验收本阶段必需能力；执行适用的仓库全套检查 | 用单测或 fixture 冒充产品验收            |
| 跨模块基础变更、失败修复、删除旧路径 | 按影响范围补回归；优先复测失败项及相关流程；影响广泛或证据已失效时扩大验证                          | 因无关小改动一律从头重跑所有通过项       |

A 主要审阅既有证据；B 以 Host/ACP 合同与相关集成测试为主，不强求安装验收。
F 对去随包和安装变更集中验证，G 做三路同候选完整收尾；相邻阶段若代码、依赖、配置和候选身份未变，
可引用同一有效证据，不机械重复执行。最终候选的完整关键用户流程与仓库要求的检查不能省略。

每次集中测试先列有限清单，连续执行并批量记录结果，无需每个通过项都停下来汇报。
独立失败项记录后继续其他不受影响的测试；共同环境失效、数据保护风险或阻塞后续验证时才停止相关范围。
通过须验证预期状态、输出和实际副作用，不能仅以“没卡住”判定。失败不得无条件重试到绿；
有代码修正、新证据或明确瞬时故障依据再重试，并保留首次失败与未知项。

已通过项没有相关变化就不重复；在实施与验证记录中记录候选身份、结果引用及失效原因，避免复制长日志和重复报告。
常规仅输出简洁测试摘要，失败时读取必要日志；不为凑覆盖率编写镜像实现的测试。
真实模型测试复用一次任务覆盖多个验收点，按有限场景执行，不做无限请求或无限轮询。
工程依据：[Google 测试层级与关键用户流程验收](https://testing.googleblog.com/2021/06/how-much-testing-is-enough.html)。

### 附录 6 分工与决策

- 执行 Agent：用户已批准，由原执行任务沿唯一计划按小切片推进。每片在实施与验证记录中记录改动范围、依据、
  对应层级测试证据、阶段桌面验收状态、未解问题、回退点和独立审阅状态；批准范围内通过后进入下一片，重大能力损失或架构取舍回用户。
- 独立审阅者：审阅计划、代码和证据并报告结论；不自动扩大实施授权，不要求用户为普通小步重复批准。
- 长会话交接：必须读取同一 active plan 和实际工作区改动；禁止靠完成标签或历史 QA 自行宣布完工。
- 用户：已批准本计划进入开发；决定会损失原生能力、移动正式数据或改变分发边界的重大取舍。

仍需证据支持的取舍：

- Pi ACP 对已接受插话和扩展交互的缺口：阶段 A 补查方案和维护成本，最迟在 D 替换前决定；
  未解决时标为未迁移，不把原生旧路作为最终 ACP 架构的另一套控制系统。
- 撤销/提交、完整交互 shell 界面目前不在默认实施范围，不因它们未决定而阻塞基础流程；
  如需扩大范围，须在实施前另行明确方案。基础文件审阅、代码展示、终端服务与工具输出是本阶段必备。

独立复审结论（2026-09-11）：已修正安装后置、模拟验收替代真实使用、新旧文档权威冲突；
补入小切片顺序、能力保留门槛与旧路径删除条件。用户随后批准补入分层测试节奏并恢复实施；这不表示适配器缺口已解决或已有功能验收完成。后续质量取决于每片实际测试与独立审阅，不能仅靠计划文本保证。
