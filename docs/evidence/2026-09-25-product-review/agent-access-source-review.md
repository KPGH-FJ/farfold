范围：Agent 目录、安装/程序选择、认证、API 服务、模型准备；当前 `eefa4df` 加共享工作区。按当前 AGENTS、PRODUCT、架构、status 和活动计划第 00 章核对。没有修改产品源码、操作安装版 UI、改变 Agent 安装或写入真实服务凭据。下列问题是源码结论，不是安装版已复现记录。

## 确认的问题

### P2 — 只有 API 连接时，账号登录/退出找不到可执行的连接

- 位置：`src-tauri/src/auth.rs:365–377`、`:504–519`、`:530–551`；`src-tauri/src/acp_client/manager.rs:221–248`、`:597–617`。
- 前提：该 Agent 已接入且提供对应协议认证能力；重启后仅打开了一个使用 Farfold API 服务的对话，没有默认来源连接。此时到账号页做 agent 型登录，或执行支持的退出登录。
- 原因：`ensure_connected` 把任意 `ready` 连接算作可认证连接，因此跳过默认连接；`run_on_ready` 又明确排除 `service.is_some()` 的连接，最后返回 `no live connection`。状态对象已提供 `service_context`，但前一个判断没有使用它。
- 影响：界面显示 Agent 已连接，登录/退出仍失败，官方认证调用没有发出。此问题不包括走 PTY 的 terminal 型登录，也不包括仍有任意默认来源连接的情况。
- 证据：**代码确定**。此次未操作真实账号；现有认证解析、正常终端退出测试没有覆盖“仅服务连接”的组合。
- 修复方向：让连接准备与认证分发使用同一来源判定，确保存在默认来源认证连接；不能把账号操作发给配置了独立 API 服务的连接。

### P2 — 取消终端登录不确认退出，拒绝 SIGHUP 的进程会使后续操作一直等待

- 位置：`src/components/AgentAuthSection.tsx:78–93`、`:303–309`；`src/components/InlineTerminal.tsx:106–127`；`src-tauri/src/pty.rs:201–231`、`:250–254`；`src-tauri/src/auth.rs:407–417`、`:435`。
- 前提：正在终端登录；登录主进程不响应 SIGHUP，或退出流程卡住；用户点击“取消终端登录”。这类进程前提没有在官方登录流程实测。
- 原因：UI 立即卸载终端并忽略 `ptyClose` 结果；后端先从表中删除 PTY，只向主 PID 发一次 SIGHUP，既不等待退出也不确认信号结果。与此同时 `await_exit` 持有 `Arc<PtySession>`，包括 master，且无界等待退出条件；从表中删除并不能保证 master 已关闭。
- 影响：若主进程不退出，登录仍持有该 Agent 的配置锁，而界面已允许重试。下一次登录或程序变更可能一直等待；旧 PTY 已不在管理表中，无法用原 ID 再次关闭。取消成功不能仅由这个命令返回 `Ok` 判定。
- 证据：**代码确定，但以进程不响应 SIGHUP 为触发前提**；不是安装版官方认证已复现，也不是所有取消都会失败。现有 `login_child_keeps_program_reserved_until_exit` 验证了锁随真实退出释放，没有验证拒绝信号分支。
- 修复方向：保留确切进程所有权到实际退出，提供有界停止/回收结果；未确认时保留可重试关闭入口和忙碌状态。

### P2 — 模型准备页的两份配置读取状态使局部重试无法恢复下一步

- 位置：`src/components/AgentSetup.tsx:97–109`、`:131–148`、`:344–368`、`:380–411`、`:464–478`；`src/components/ServicePicker.tsx:31–50`、`:110–117`。
- 前提：已连接，准备流程选择 API；Setup 的 `Promise.all(getServiceCapabilities, listCredentials)` 曾发生一次暂时失败，然后进入第三步。第三步 ServicePicker 的独立读取/重试成功，用户能够选中兼容服务和模型。
- 原因：`serviceValid` 仍依赖 Setup 外层的 `capability` 和 `services`。ServicePicker 重试只更新自己的数据，不更新外层失败状态；外层重试入口只在第二步出现。进入第三步不检查外层读取是否成功。
- 影响：模型明明可选且已选，仍只显示“请选择兼容配置”，测试入口和“下一步”持续禁用。用户必须猜到应退回第二步重试，或关闭再打开；本步显示的重试不能恢复整条流程。
- 证据：**代码确定**的失败状态组合；本轮未在安装版制造 IPC 读取故障。
- 修复方向：让准备页和选择器共享一次读取结果/错误状态，或使本步重试同时刷新实际用于判定的外层状态。

## 单独保留的观察，不列为已经证实的丢稿缺陷

`ServicePicker.tsx:51–56` 会在选中记录的 revision 改变后自动调用 `onChange`。使用当前源码经 TypeScript 转译执行该 effect 的纯内存探针，得到 **0 次用户选择事件、1 次 onChange**，新值为同一服务/模型的新 revision。探针未调用 IPC 或 UI。

`EmptyState.tsx:418–424` 收到该回调后更新 service，`:151–225` 会重新准备草稿；由于选择器只在 `WorkspacePopover.tsx:86–104` 展开时挂载，可能出现“保存 API 修改后，仅打开模型菜单就重新连接”的体验。`credentials.rs:221–224` 中模型列表变化、Key 轮换和地址/接口变更都会改变 revision。它需要与 PRODUCT 的“保存不自动重连、选择才授权本次使用”进一步核对。

**不声称推理设置已丢失或已建立对话换源。** `EmptyState.tsx:231–255` 仍可能把原草稿选项保留下来，后端对已建立/恢复对话另有来源身份校验；本轮没有端到端覆盖这个弹层触发路径。
