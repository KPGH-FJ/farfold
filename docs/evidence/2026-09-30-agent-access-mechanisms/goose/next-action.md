# Goose 官方服务配置：下一片动作设计

核对日期：2026-09-30。源码基线：`85235cd6768045396258ff0bf66cdee55403a1b6`。本文件是[现有 Goose 失败证据](README.md)对应的只读设计记录，实施顺序仍归[唯一活动计划 §3.4](../../../../plans/agent-access.md#34-配方与通用执行机制)。本次仅查源码与官方资料，没有运行配置程序、操作账号或修改产品源码。

建议增加一个共用的“配置模型服务”准备动作：接入层用有来源、有适用范围的配方声明入口，用户查看实际程序与参数后显式运行，共用现有内嵌终端与操作管理。保持协议认证方法原样；程序依赖状态也保持原义。

## 1. 事实与复用判断

当前安装证据只证明 Goose 1.52.0 安装、连接成功；模型读取因服务配置缺失失败，错误为 `-32603`，不是 `AUTH_REQUIRED`。配置成功、首条消息及续接仍未验证。

| 现有入口                                                  | 能否承载                                         | 限制及最小处理                                                                                                        |
| --------------------------------------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `ManualAuthSection` / `auth_manual_run`                   | 能执行用户明确保存的绝对路径程序和参数，共用 PTY | 用户需手工填写命令，界面按登录解释，配置按 Agent/方法保存。不能把配方偷偷保存成用户命令，也不能直接继承其凭据交付策略 |
| `PreparationDependency`                                   | 不能表达服务配置                                 | 它描述程序依赖的发现、安装与用途；配置程序退出不等于依赖齐全、账号可用或模型请求成功                                  |

| `AuthActivity`、`BufferedLoginTerminal`、`InlineTerminal` | 可复用操作所有权和终端视图                       | 补充动作目的、标题和完成语义；不得伪造认证方法来获得终端，也不另建第二套操作状态机                                    |

## 2. 与协议认证的关系

Goose 1.52.0 声明的 `goose-provider` 是 Agent 方法。其标准 `authenticate` 处理直接返回空成功响应，未执行服务配置或凭据验证。因此认证请求完成不能证明本案例已解决。[握手声明](https://raw.githubusercontent.com/block/goose/v1.52.0/crates/goose/src/acp/server.rs)、[认证处理，第 36–39 行](https://github.com/block/goose/blob/v1.52.0/crates/goose/src/acp/server/dispatch.rs#L36-L39)。

保留该方法及原始 envelope，继续按协议发送 `authenticate`。配方动作独立列为“配置模型服务”，可以记录关联的方法 ID 用于位置提示，但它不是新 `authMethods`，不会把 Agent 改成 Terminal。不能从 description 提取可执行命令；标准 Terminal 的同一程序及基础参数追加规则保持不变。

官方 `configure` 要求交互终端；已有配置时还可调整扩展、工具权限等。凭据可能逐项保存，部分失败会清除配置文件，但不能据此保证已保存秘密被撤销；首次配置流程也可能捕获失败后正常返回。[官方配置入口及处理](https://raw.githubusercontent.com/block/goose/v1.52.0/crates/goose-cli/src/commands/configure.rs)。

服务测试实际调用流式模型请求；这不是纯本地编辑。[官方服务测试](https://raw.githubusercontent.com/block/goose/v1.52.0/crates/goose/src/providers/provider_test.rs)。`GOOSE_PROVIDER` / `GOOSE_MODEL` 环境值优先于配置文件，故看到配置文件或程序退出仍不足以证明有效服务已改变。[服务与模型解析](https://raw.githubusercontent.com/block/goose/v1.52.0/crates/goose/src/config/providers.rs)。

## 3. 最小共享动作契约

先为已核实的一个动作落实以下边界，再用第二个真实机制验证并冻结 schema；本样本本身不完成计划中的配方里程碑。

| 字段或行为       | 建议                                                                                                                          |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `id` / `purpose` | 稳定动作 ID；目的先支持 `service_configuration`，映射共用文案“配置模型服务”                                                   |
| `transport`      | 首片只需 `terminal`，不做脚本、工作流或任意回调执行器                                                                         |
| 调用预览         | 返回当前选定程序的绝对路径及参数数组，供用户审阅；不返回环境值或秘密                                                          |
| 适用条件         | 配方在 `acp_client/recipes/` 内核实目录身份、发行/安装来源、当前启动形状、官方版本证据；不能仅按程序名称匹配                  |
| Goose 首样本     | 已核实的目录二进制、版本 1.52.0、当前参数恰为 `["acp"]`、条目环境为空；配置调用使用同一已选二进制，参数替换为 `["configure"]` |
| 来源             | 固定官方标签、核对日期、字段适用范围；版本或声明超出已核实范围时不提供该补充，保留纯协议及手动命令入口                        |
| 可执行条件       | 已注册程序、沿用已有设置、目录有效、没有冲突操作；读取动作信息不运行子进程                                                    |
| 退出语义         | 只报告程序已结束或停止未确认；不生成“已登录”“可用”的事实                                                                      |

该版本范围只约束补充动作的已核实适用性，不限制 Agent 的安装、升级或纯协议连接。未知版本、额外启动参数、自定义环境或用户自定义命令不自动套用此样本；后续核实后可以扩展声明。命令参数不得写成 `acp configure`，不得经 shell 拼接执行。

建议通用运行接口接收 Agent、动作 ID、原目录、原使用来源、现有 attempt ID，以及用户刚审阅的非秘密程序与参数。后端取得现有配置保护后重新读取当前注册目标及配方，重新派生命令并与审阅值比较；已换程序、动作失效或来源改变时停止并要求重新查看。客户端参数不成为任意命令执行通道；无须新增持久身份或操作账本。

## 4. 共用交互与返回路径

1. 在共用账号/服务区域显示适用动作；模型读取失败处可以导航至同一动作。只要条件适用即可手动打开，不通过解析英文错误或读取配置秘密判断“未配置”。通用 `-32603` 不自动变成认证失败。
2. 同一准备容器内展开实际程序、参数、官方来源，以及简短说明：“将打开此程序的官方配置界面，可修改服务、凭据及其他设置，也可能发送服务测试请求。停止操作不会撤销已经保存的内容。”用户点“运行官方配置”才执行。
3. 内嵌终端显示官方交互；暂离后重开仍是同一个操作。退出、失败、取消和停止未确认沿用现有状态，不重开第二个进程。终端可见不代表另建 Goose 页面。
4. 配置程序结束后停留原准备位置，显示“配置程序已结束”；安全范围内重新检查原目录连接，单独报告重查结果。模型读取由用户显式选择“重新读取模型”，不自动切页引发隐藏读取。
5. 真实 `session/new` 成功仅更新模型读取阶段；真实请求留下的认证要求仍保留，直到实际请求成功。需要短测时由用户主动触发；Farfold 不自动发送原稿。官方配置程序自己发出的服务测试按前述说明处理。
6. 返回原稿保持原目录、服务来源、所选模型、推理等级和内容。已建立对话仍遵守既有模型与来源约束；新配置不自动替换旧对话选择。

## 5. 执行、来源与秘密边界

- 沿用 `attempts`、`configuration_guard`、操作 lease、`PtyManager` 和退出回收。启动前检查早到的取消；保护持有到自身子进程回收确认，不能因页面关闭或请求超时提前释放。
- 配置可能改共享设置，必须拒绝同 Agent 的忙任务、待审批和结果未知操作。当前 `reserve_account_change` 只保留沿用已有设置的连接，前端忙任务检查覆盖同 Agent 的所有来源；新动作不得把前端检查当后端保证。实现时须在现有准入机制中补足动作所需的同 Agent 忙任务检查/保留，不扩大仅重查动作的关闭范围，也不关闭 API 连接。
- 当前选了 API 服务时不运行此已有设置配置动作。不给动作偷偷清空 `source`，也不复用它绕过服务补登录边界；改变使用方式由用户正常选择。
- 复用终端管理，不照搬 `auth::environment_for`：它会解析注册环境中的 Keychain 引用并执行既有凭据授权交付。首样本只承载已核实的空条目环境，继承正常用户环境与 HOME，不新增 Keychain 读取、不调用 `credentials::apply`、不注入所选服务 Key。用户本来的环境仍可能含凭据，不能声称子进程没有任何秘密。后续支持非空环境前须单独核实交付权限，不 `env_clear`、不建私有 HOME。
- Farfold 不读取秘密来猜配置结果，不替官方程序写配置或凭据；用户在官方终端输入产生的保存由该程序负责。取消只停止本轮拥有的进程，不删除官方已保存内容。
- 终端数据留在既有有界内存缓冲，不写日志、设置或证据；证据只保留脱敏的操作、退出/失败事实与必要界面，避开输入凭据及完整终端内容。

## 6. 实施落点与必要验证

最小改动落点为接入层配方及准备动作字段、通用动作 IPC、共用认证操作描述/文案、现有账号区域的动作入口。复用已有终端输出及生命周期，不调整 `PreparationDependency` 的安装/使用 readiness，也不新增品牌前端分支。若抽取共享执行函数，保持手动命令和标准协议认证现有路径与来源保护。

必要行为回归：

- 标准 Agent 方法含命令描述仍只走 `authenticate`；标准 Terminal 仍使用声明的参数规则，旧扩展不能覆盖它。配方不匹配、过期或目标变更时只禁用补充动作。
- 用户未点击、早到取消、重复点击、忙任务及 API 来源不产生配置子进程；审阅后程序更换不能执行旧命令。忙 API 对话须有后端竞态用例。
- 暂离/重开共享同一终端；取消和未知退出不提前释放保护；配置失败可重试，旧程序选择与原稿不变。
- 退出零、空认证响应或重新握手不清请求级认证失败；重新读取模型也不清请求级失败。重查失败保留可读错误，重试成功不自动发送消息。
- 配置动作不从 Farfold Keychain 加载或交付已保存 Key，不持久化终端内容；现有服务交付与手动命令行为另有回归，不因复用改变。

安装版出口仍须在唯一 `/Applications/Farfold.app` 验证：当前失败入口 → 审阅并显式配置 → 暂离/取消/重试 → 原目标重查 → 真实模型读取 → 用户选择模型 → 真实首发 → 返回及续接；同时确认其他忙对话未关闭、原模型/推理与原稿保留、本轮子进程退出。账号条件不足时保留未测，不用官方短测或程序退出代替 Farfold 首发/续接证据。

本记录已完成源码与固定官方来源核对；新动作未实现，Goose 配置、账号、模型读取、真实请求与安装版交互均未新增验证。
