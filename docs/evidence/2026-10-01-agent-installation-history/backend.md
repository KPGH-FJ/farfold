# 整程序卸载后的历史清理

本片只修改通用安装清单及临时目录测试。当前工作区不是安装版验收结果；正式应用、用户数据、真实 Agent 和外部配置没有由本子任务操作。

## 触发与修复

真实选择事务从受管程序 A 切到 B 时，`installPrevious.<id>` 保留 A 的 `command`/`args`。原卸载路径删除 A 的目录与安装收据，却只清理伴随程序的 `programPath`。下次冷读清单会根据旧 `command`/`args` 把已卸载的 A 重新列成未核实程序；旧单测直接替换选择，没有经过保存前一次选择的事务，因而未覆盖此分支。

卸载仍必须先取得现有安装收据、确认其受管目录归属，并拒绝任何当前接入仍指向该目录的情形。新增清理只针对这一个已确认删除的目录：

- 整启动的 `command` 或独立绝对路径参数依赖它时，在一次 `set_setting` 中同时清空该快照的 `command` 和 `args`。独立 `programPath`、来源、版本及其他字段保留；原 `programPath` 清理规则单独生效。
- 既有清单中没有受管归属、但路径或整启动指向该目录的旧条目也移除。它们只失去这项安装元数据，不获得卸载权限；外部别名文件保留。
- 继续扫描 `installPrevious.*` 的公开字段，覆盖另一 Agent 的历史及无实体收据的旧快照；不扫描任意嵌套 JSON 或其他设置，也不按缺文件、版本或未知字段推断删除归属。

没有新增账本、版本固定、凭据读取、用户配置改写或 Agent 专属分支。现有返回旧安装入口在 `command` 已清空后按原“没有可返回的安装”出口处理；仍有效的独立程序选择保留。

## 保存失败边界

文件删除与 SQLite 保存不是一个事务。目录已删而快照或清单保存失败时，操作明确返回失败，受管安装收据仍保留到最后一次成功保存，供同一目录的明确重试使用。`command`/`args` 只在一次 JSON 保存中同时变化，失败不会留下半个启动参数组合；不能把这项保证称为跨所有 Agent、设置与文件系统的全局原子提交。

删除目录后仍复用既有有界路径判断处理悬空别名，不删除别名本身，不改变当前 B 的启动或原会话/草稿。在后续保存失败时，其他已清理的失效引用可能已经更新，仍通过保留的收据完成重试。

## 受控验证

- 初始三组红例见 [backend-red.json](backend-red.json)；随后将二进制/脚本和两类保存失败拆成五个独立用例。
- 最终 [backend-red-literal.json](backend-red-literal.json) 与 [原日志](backend-red-literal.log)：五项全部失败。冷读断言直接排除 A 的原始 `command`/`args` 组合、收据 id 和目录字面路径，不仅依赖已删除目录的规范化结果。
- [backend-green-first.json](backend-green-first.json)：同样五项全部通过。
- [backend-focused-final.json](backend-focused-final.json)：全部安装清单与候选安装定向检查的最终命令、日志和退出码；最终跨 Agent 原始条目的路径为外部 `/bin/sh`，仅绝对脚本参数依赖被卸载目录。

五项用例分别验证真实 `commit_candidate(A→B)` 后卸载 A 的二进制与脚本启动、跨 Agent 当前引用拒卸载及历史/原始条目精确清理、快照保存失败的字段原子性、安装收据保存失败后的冷读重试。每次均使用真实临时文件与独立 SQLite 存储，重新打开存储并以空发现结果读取清单。原 B、会话索引及模型/推理选择、未发草稿、凭据引用标记与外部别名文件保持。

测试没有启动上述脚本、真实 Agent 或正式应用。安装版验证由根任务使用新的受管样本完成，不卸载原程序；结果需单独记录。
