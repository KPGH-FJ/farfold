## 已证实的问题

### I-01：样本文字文件未显示正文，重试后仍受阻，后续 HTML 打开也被前一检查阻挡

**S2；现象高置信；原因未知。** 涉及文件链接到内容栏预览这条任务路径，不推广到所有文件或所有机器。

- 路径：本轮回复出现“文字样本”和“网页样本”链接 → 点击文字样本 → 等待 → “重新打开”一次 → 点击网页样本。
- [U019](../../file-inventory.html#file-224) 和 [U020](../../file-inventory.html#file-226) 都显示 `sample.md` 与“正在打开文件…”，没有正文。[U021](../../file-inventory.html#file-228) 已显示“文件检查尚未返回，后台可能仍在检查”，并提供“重新打开”。U019 与 U021 的采集时刻相隔约 55 秒；这不是对内部超时阈值的测量。
- `actions.jsonl` 第 15 次操作记录一次重试后重新显示加载，第 16 次操作及 [U022](../../file-inventory.html#file-230) 又出现同一未返回提示。[U023](../../file-inventory.html#file-232) 切到 `sample.html` 后明确显示“已有文件检查尚未结束，本次未开始新检查”。对应 AX 也一致。
- 用户影响：已经获得的文字/网页链接无法在本轮内容栏读到正文；更换另一文件也未恢复该路径。现有提示最终建议查看系统访问提示或保存后退出重开，恢复成本较大。
- 正常保护/反例：内容栏显示目标文件名及可展开路径；没有假装成功，也没有静默继续检查；重试、返回文件与输出、收起内容栏均有可见入口。聊天搜索仍能使用，不能称整个应用卡死。
- 改进方向：先定位这两个样本在当前环境下为何未返回；在不要求用户丢失工作或强退的前提下验证可恢复路径。具体归因于系统权限、环境、应用或某个后台模块，当前证据都不足。
- 复验标准：相同链接显示可读正文；失败时能看懂当前状态并退出/恢复预览；同一未完成检查不应让后续文件一直只有等待说明。若设计确实需要串行，需证明其结束与恢复路径。

### I-02：起步页暗示只有处理文件才选目录，纯文字发送却要求目录

**S3；高置信。** 这是前置条件表达不一致，不是“产品必须支持无目录发送”的实现结论。

- 路径：[U009](../../file-inventory.html#file-204) 无工作文件夹起步页 → 输入不使用工具、只回复一句话的文本 → 点击发送 → [U010](../../file-inventory.html#file-206) 系统目录选择 → 取消 → [U011](../../file-inventory.html#file-208)。
- U009 引导是“写下想做的事；需要处理文件时再选文件夹。”U010 仍要求选择目录。U011 同屏保留这句引导，同时新增“选择工作文件夹后即可发送”。两个条件表达直接冲突。
- 用户影响：首次使用者按页面说明完成纯文字输入后才发现额外条件；取消后仍需要重新理解为何必须选目录。
- 正常保护/反例：取消后原文完整留在输入区，界面显示补救提示；本帧没有出现已发送消息。之后选择目录可以继续，不能称草稿丢失或发送彻底失败。
- 改进方向：起步说明明确发送前需要工作文件夹，并用用户任务语言解释用途；保留当前取消后保存草稿的行为。是否另做无目录对话属于产品决策，不能由本缺陷擅自扩大范围。
- 复验标准：读起步文案就能预测首次发送会发生什么；目录取消、重新选择后的文案与实际行为一致。

### I-03：已有目录的空草稿在大窗口中显著收窄，常用设置散成多行

**S3；现象高置信；两个稳定草稿状态已见，普遍性待验证。** 这是布局与扫描成本问题，未见按钮不可点或内容被裁掉。

- [U008](../../file-inventory.html#file-202) 的窗口有大量可用横向空间，但输入区明显窄于同尺寸下的 [U009](../../file-inventory.html#file-204) 起步输入区和 [U015](../../file-inventory.html#file-216) 对话输入区。Agent/模型、思考、权限、命令/发送分别换行，目录选择又在输入区上方。
- [U045](../../file-inventory.html#file-276) 是另一时刻的稳定空草稿，目录已回到 TR，内容栏已收起、没有“正在创建”提示，仍出现窄输入区和多行控制。它加强了相同条件下的复现证据，但不是不同设备或窗口尺寸的独立样本。
- 用户影响：同一组常用选择在“有目录空草稿”与前后步骤改变排布，需要上下扫描更多行，输入区域也显得局促。
- 反例与边界：U015 首次回复后的输入区恢复宽排布；U018 开内容栏后因可用宽度减小而换行具有合理原因，不能与 U008 的空白大窗口直接等同。U013 背景被弹窗遮挡，不作为另一次稳定布局证明。
- 改进方向：检查稳定空草稿的宽度与对话输入区是否应共享一套尺寸规则，保留必要的自适应换行。继续复现不同目录与窗口宽度，不从这些图断言具体 CSS 原因。
- 复验标准：在同一大窗口来回经过无目录、目录准备完成、首条消息前后，输入区与设置的位置变化有可理解的理由，常用控制不会因空态而无谓堆叠。

### I-04：导出提交后整组对话菜单禁用，没有可见进行中或结果说明

**S2；当前样本任务受阻与反馈缺失均为高置信；原因未知。** U036 的延迟复查将本项从原 S3 上调。仅断言本次选定路径尚无文件，不推断所有导出都会失败。

- 路径：[U027](../../file-inventory.html#file-240) 打开对话菜单 → actions 23 出现系统保存面板 → [U028](../../file-inventory.html#file-242) 回到应用，菜单所有项目均变灰且 AX 标为 disabled → actions 24 关闭菜单 → actions 25 再开，全部项目仍 disabled。
- U028 图片与 AX 没有导出中、已完成、失败或保存位置反馈。actions 25 在 U028 约 34 秒后仍记录同样禁用的菜单。用户无法从这些帧判断应等待、重试，还是已完成。
- 延迟复查：[U036](../../file-inventory.html#file-258) 在离开到设置、查看 Claude 程序并返回后，全部菜单仍禁用；它与 U028 相隔约 8 分 56 秒。审阅者于 09:28:47 UTC 只检查本轮指定产物 `fixtures/uiux-conversation-export.md` 的存在性，结果为 `False`，未读取任何用户文件内容。
- 用户影响：本次选定产物尚未获得，且不只是导出项，重命名、收藏、分组等同组操作也不可用且没有解释；用户可能重复尝试导出，或放弃本次结果。
- 反例与边界：关闭菜单后聊天配置恢复可用，U029 可以进入设置；不能称整个应用锁死。本次仅额外检查已指定审查产物的存在性；未确认其他路径，不能断言没有生成任何文件，也没有读取文件内容。
- 改进方向：对用户可见地说明导出状态与保存结果；禁用其他操作时给出具体原因；完成或失败后恢复入口。先确认真实落盘与结束状态，再决定是否为执行故障。
- 复验标准：保存面板确认后出现可理解的进度或结果，最终能确定文件所在位置或失败原因；重新打开菜单不会只得到无说明的长期灰态。

### I-05：清除数据的不可恢复说明被挤成极窄纵列，难以阅读

**S2；高置信的视觉可读性问题。** 涉及破坏性操作的解释，优先于普通排版细节；只打开清除范围预览后取消，未执行确认清除，不推断实际删除安全性。

- 路径：[U029](../../file-inventory.html#file-244) 设置 → 你的数据如何保存 → [U030](../../file-inventory.html#file-246)“数据与隐私”。
- 上半段四类数据说明排版正常；到了“清除 Farfold 数据”，标题变为多个单字纵排，正文也只剩约一两个汉字宽的列，一直向下延伸到当前可视区下沿。右侧“清除 Farfold 数据…”按钮却占据其余宽度。
- AX 能读到完整的“无法恢复”“进行中或结果未确认的任务、安装与账号操作会先阻止清除”等内容，但图中用户无法顺畅阅读这一段。AX 完整是文本存在的证据，不是视觉可读的证据。
- 用户影响：用户在触发清除前难以理解删除范围、不可恢复性和阻止条件，且难以继续理解后续卸载说明。
- 反例与边界：关闭和“知道了”均可见；上半段数据归属说明清楚。未验证滚动到底的效果，但滚动本身无法解释为何文字列如此狭窄；后续 U031 已展开范围预览：截图只显示列表上半部，AX 列出完整范围及取消/确认按钮；不能据此说全部范围和底部按钮视觉可读。actions 27 正常取消。
- 改进方向：给风险说明保留正常正文宽度，将清除入口独立排布；在这段说明和完整卸载之间保持可读顺序。不要仅因 AX 文本完整而关闭此问题。
- 复验标准：当前大窗口与更窄窗口均能正常横向阅读整段不可恢复说明，清除入口不挤压说明；后续确认另行验证。

### I-06：命令菜单的长说明跨行覆盖，无法可靠对应条目

**S2；高置信；当前 Codex 的长命令列表样本。** 未选择或执行命令，不推广到只有短命令的 Agent。

- 路径：在本轮完成回复的对话里打开“命令与模板”，得到 [U037](../../file-inventory.html#file-260)。
- 菜单上半段 `/plan`、`/mcp`、`/skills` 等还能对应名称与说明；从 `/rename`、`/logout` 附近向下，多个长说明占据相同区域，密集覆盖到弹出框底部，部分长命令名也跨多行。AX 有独立按钮与说明，但视觉上无法可靠分辨哪个说明属于哪个条目。
- 用户影响：用户难以读取用途并选择正确命令；这个入口的浏览选择任务显著受阻。未观察到误点击或错误执行，因此不宣称已执行错误操作。
- 反例与边界：短条目仍可读，菜单打开后其他界面仍在；不能称所有命令失效。其条目来自 Agent 不改变 Farfold 负责共用菜单呈现的界面现象，具体布局根因未查。
- 改进方向：让长描述与命令名具有明确条目边界和足够行高，按容器容量提供可滚动列表与适当摘要；不通过改写 Agent 命令内容来掩盖布局问题。
- 复验标准：当前长列表和短列表都能逐项读懂，滚动、键盘选中与鼠标目标不会因长说明重叠而混淆；选择/执行另行验证。
