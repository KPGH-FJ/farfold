# 第 12 周期 Amp 官方账号入口

用户反馈 Farfold 里启动 Amp 设置终端登录失败。已登记的适配器 0.9.0 通过 ACP 声明 `Amp API Key Setup`，命令为该适配器的 `--setup`，用于独立的 API 密钥。厂商 CLI 0.0.1790740844-g023754 已安装，原厂商账号通过 `amp login` 保存。登录前的账号列表显示无保存账号，官方原线程列表一次只读尝试要求认证。旧终端失败的具体退出原因未观察到。[适配器登录声明](https://github.com/tao12345666333/amp-acp/blob/v0.9.0/src/server.ts#L157-L169) · [厂商账号流程](https://ampcode.com/docs/cli#manage-cli-accounts) · [原核对](../2026-11-16-cycle12-eight-check/README.md)

Farfold 复用共用准备流程，提供单独的「使用官方程序登录账号」。确认页显示所选厂商可执行文件和固定参数 `login`。根据当前登记与两条管理记录核对原适配器和实际伴随程序，执行前再次核对。原密钥入口保留。当继承环境、现有密钥授权、独立适配器密钥文件或连接方式会覆盖账号来源时拦下。检查密钥文件仅依据文件状态；终端复用已有执行器，只使用常规环境。终端结束后仍须核实际账号、原线程和生效来源。

Amp 定向样本覆盖同一登记的两条入口、非归属或过期选择、密钥来源冲突、连接方式精确条件及凭据路径。相关 108 个前端测试、全量前端 10,951 项、类型与格式检查通过。

macOS 0.1.7 正式版从「探索 Agent → Amp 管理设置 → 账号与服务 → 接入方式」能同时看到原 `Amp API Key Setup` 和「使用官方程序登录账号」。选择新方式后需点「继续」，「查看详情」显示原已安装程序的绝对路径及唯一参数 `login`，页面另有「启动登录终端」。本次未替用户启动登录或输入凭据。厂商账号及同一原线程的真实读取仍待验。

正式构建固定 2,634 项输入。严格发布 Clippy 与最终发布版准备流程 16 项通过。安装前后 236,586 项保护记录摘要一致，独立元数据副本完整，重复应用已移除。[安装与检查回执](results.json)

## 用户启动后的复验

用户实际按「启动登录终端」收到来源检查错误，Farfold 未启动厂商程序。安装版同面板复核旧错误存在。登记中的确有原适配器单独使用的凭据文件，核查限文件是否存在、大小是否为零及文件类型。该文件供独立适配器启动时读取，旧入口因此误拦截直接启动官方 CLI。补丁移除了该文件检查，且用合成凭据文件存在的样本验证厂商登录仍可启动。继续核对实际继承的环境、选中程序的归属和请求参数。[适配器启动用的环境](https://github.com/tao12345666333/amp-acp/blob/v0.9.0/src/index.ts#L144-L177)

适配器 0.9.0 和当前目录 0.13.0 仍会在自身启动时把独立保存的密钥放入环境，可能优先于厂商 CLI 的账号。直接登录后单独核原账户及原线程，并核 Farfold 对话实际用的来源。两条原凭据路径均保留。

本机 MiniMax Code 0.2.7 使用 Farfold 登记的 Node 与官方包内 `cli.js`。实际以完全相同的程序执行 `--help` 自然返回 0，确认厂商普通终端名称 `mcode`。用该登记的绝对程序路径与脚本路径，调用时省略末尾 `acp` 即可打开官方交互界面，在 `/model` 设置并明确选中小米模型。两种调用共用该正常配置没有额外配置目录覆盖。没有安装第二份程序，也没有执行模型请求。[官方发行包](https://registry.npmjs.org/@minimax-ai/code/-/code-0.2.7.tgz)

正式版更新后，在原页面实际按「启动登录终端」。前次错误未出现，界面显示终端在途，系统独立观察到所选官方程序在运行。原适配器文件仍存在。用户完成官方账号登录后再核认证及 Farfold 对话来源。安装前后 236,586 项保护记录摘要一致，本次前端 76 项、Rust 定向 5 项通过。[修复回执](account-start-fix.json)
