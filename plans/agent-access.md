## 0. 目标与完成定义

**目标：** 用户在 Farfold 内完成发现、安装或升级、条件式登录或选择 API、选模型、发送第一条消息，并能返回原任务继续使用。官方网页授权或注册可以打开浏览器；其余操作不要求打开 Terminal.app 或手改配置文件。免登录、已有凭据和可选登录允许直接尝试，不统一强制认证。

范围覆盖官方目录全部条目、本机发现与对应目录条目的合并入口、用户自定义入口，以及目录外可核实官方接入面的 Agent。目录外条目先确认官方 ACP、SDK 或 CLI 是否满足现有产品能力；不通过第二 Agent 循环、模型代理、私有 HOME 或修改外部 Agent 扩大覆盖。

### 0.2 接入组合路径与上市门槛

J0 是本计划用于组织 J1、J6、J2 的**组合验证路径**，不是另一份产品契约：

发现/选 Agent → 安装或选择已有程序 → 连接 → 按实际缺失条件处理账号/API → 读取并选择模型 → 返回原稿 → 用户显式发送 → 获得真实回复。随后按适用能力执行续接和管理用例。步骤可跳过；返回、取消和重启均不自动发送。

- 连接成功、认证成功、模型读取成功与实际模型请求成功分别记账到覆盖表；不建立产品事件账本。
- 所有宣称可用的条目和路线必须在最终同一安装候选上取得对应成功证据；可选能力确实不存在时，验证其诚实出口。
- 全目录目标继续保留。条件缺失、未测、失败都进入上市缺口，填满表格不等于上市完成。外部限制须有证据；接受具体发布例外需明确决策，不能默认缩小承诺。
- J0 不代替 J3–J5、程序/密钥管理和已有工作台要求。接入成功不能关闭停止、审批、并行、历史恢复等其他缺口。
- 实际记录用户操作、下载、浏览器授权及模型等待耗时。取消未经基准支持的统一“从零 ≤ 2 分钟”硬门槛；若后续设体验目标，先明确网络、缓存、账号与模型条件，功能判定和耗时判定分开。

## 3. 目标架构：独立事实 + 六个通用机制 + 声明式配方

### 3.1 状态事实与界面

不将未安装→需升级→未登录→可用实现为所有 Agent 必走的线性链。程序、连接、认证、所选服务/模型、请求结果和当前操作分别保存事实，再计算主动作：

| 当前事实                         | 界面与主要动作                        | 判定边界                               |
| -------------------------------- | ------------------------------------- | -------------------------------------- |
| 缺少程序或已核实依赖             | 安装/选择已有程序                     | 已有程序可以跳过安装                   |
| 已核实的依赖不满足或兼容失败     | 说明原因，提供检查/安装兼容程序       | 不因版本未知或低于经验值直接禁用       |
| 未连接                           | 连接                                  | initialize 成功只变为“已连接”          |
| 明确认证要求                     | 登录/选择兼容服务                     | 免登录、已有设置或未知状态不被统一拦截 |
| 缺少必要的服务/模型选择          | 选择服务/模型                         | 不覆盖旧会话固定选择                   |
| 已连接、无明确阻碍，尚无请求证据 | 允许开始对话，明确尚未验证请求        | 不冒称“可用”，也不强制隐藏发送短测     |
| 当前配置已有实际成功请求         | 可显示“可用”并开始对话                | 结果只覆盖该程序、来源、模型与条件     |
| 安装/登录/检查正在进行           | 显示进度、暂离与允许的取消            | 重复点击不产生重复操作                 |
| 超时、取消未确认或断线结果不明   | 显示“结果未知”及有依据的检查/结束动作 | 不改成成功，不自动重试未知请求         |

主按钮按当前最需要处理的条件决定；管理动作仍可访问，不把全部维度压成一个不可解释的布尔值。用户文案遵守 PRODUCT 术语表，不展示工程状态名。

请求成功证据依附当前已有连接和选择；程序/参数/官方环境、账号、服务地址/接口/密钥修订、模型或推理选择变化、断线/重启、认证失败、相关请求失败后按作用范围失效。429/额度错误与登录失败分别显示原因，不要求用户为所有请求错误重新登录。旧请求的成功记录不能覆盖新选择，界面暂离也不能使迟到结果写回别的入口。不新增持久“可用”表、连接代次或会话一致性账本。

### 3.2 六个机制与交付边界

| 机制               | 输入与行为                                                                                                       | 明确禁止/必要出口                                                                                                                                               | 主要落点                                                             |
| ------------------ | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |

| M2 协议认证        | 按 agent 方法调用 authenticate，记录当前操作、等待/暂离/取消/超时，再检查所属目标                                | agent 不等于必经浏览器；成功回执、登录、权益和模型请求分开；未知请求不自动重发                                                                                  | auth、auth/attempts、auth_activity                                   |
| M3 内嵌终端认证    | typed terminal 使用同一已配置程序和基础启动参数，追加声明 args/env，等待退出后按安全范围重新连接                 | typed descriptor 不提供另一个 command；退出零仅是该登录流程成功信号。旧扩展及其他官方命令单独核验，超出已配置命令走用户显式配置                                 | auth、pty、InlineTerminal、auth_actions                              |

### 3.3 操作保护与重连范围

统一界面中的操作状态，但保留不同后端职责：认证操作身份防重复与迟到结果，配置互斥防安装/服务替换竞态，相关工作保护防破坏运行/审批/未知请求。先复现误拦并证明哪个条件可删，再缩小保护范围。

| 操作场景                              | 并发与返回要求                                                                            |
| ------------------------------------- | ----------------------------------------------------------------------------------------- |
| 同一目标重复登录、登录中又取消/切方法 | 单一当前认证操作；取消需完成确认，旧结果不能覆盖新操作                                    |
| 登录期间安装/切程序/改服务            | 冲突变更串行或明确拒绝；不出现新程序配旧凭据的混合检查                                    |
| 登录已成功但仍有相关工作              | 不调用全 Agent 断开来完成检查；能独立检查则核实能力后使用，否则显示稍后检查，已有任务继续 |
| 换账号/退出会影响共享凭据或已有连接   | 先查明官方作用范围，列出受影响会话；无法保证旧任务时保留保护，不能仅靠提醒放行            |
| 其他 Agent/不相干入口有工作           | 不全局封锁；暂离/返回恢复原目标和输入                                                     |
| 停止未确认、审批待处理、请求结果未知  | 保护相关工作；不得自动重连后补发未知消息                                                  |

当前 agent_disconnect 仍用于显式全 Agent 断开；认证完成后的检查已改为 auth_recheck，仅在原目录的已有设置连接原子空闲时替换。其他目录与 API 连接保留；API 检查继续由原服务连接入口处理。新方案复用现有管理器与操作身份，不新建第二套生命周期协调器。作用范围的受控测试与安装结果分列，继续补真实并发覆盖。

### 3.4 配方与通用执行机制

建议落点：`src-tauri/src/acp_client/recipes/`。一份权威注册入口可以由多个数据模块组成，遵守单文件 ≤1.5k 行；不为“单文件”目标制造大文件。

配方描述已核实的事实，执行机制负责验证、合并、交付与回收。建议先用如下类型边界做两个真实样本，再冻结 schema：

```text
match:
  registryId / 已核验的接入标识和启动形状
  appliesTo: 官方组件及已核实的协议/版本范围
compatibility:
  官方程序/组件依赖要求、检查方式、升级入口
dependencies:
  官方分发、所需程序、可选安装路线
authSupplement:
  精确方法匹配、官方说明/注册入口
  旧扩展的声明解释或用户显式配置提示
service:
  支持的接口格式、官方交付通道
  有类型的字段映射与配置合并约束
install:
  目录未表达的官方依赖及 uvx 分发资料
sources:
  fieldPath、官方 URL/源码定位、核对日期、适用范围
```

- 优先级：当前协议声明 → 已核验的官方扩展 → 适用范围内的配方补充 → 用户显式配置。用户选择的使用方式仍有效；相互冲突时说明原因，不静默替用户选择。
- 标准字段缺省 type 按协议解释为 agent；配方不能按品牌把它强改成 terminal，也不把 description 的自然语言解析成命令。未知 envelope 保留，未知方法不冒充支持。
- typed terminal 的调用语义不被旧扩展覆盖；旧扩展的不同程序须有精确声明/启动形状依据，并满足目录或用户显式配置的命令边界。
- sources 必须能定位每个非平凡字段；缺出处、范围不匹配或声明已变时停用该补充，继续纯协议或显式配置路径。内置配方随源码发布，不从项目目录读取或动态执行脚本。
- mapping 是有限的、有类型的变换与合并规则，不接受任意代码、shell 片段或秘密常量。保留现有非秘密服务身份、冲突检查和恢复来源保护。
- 秘密仅在当前授权交付阶段进入官方通道，不放入会被启动诊断保存的配置对象；序列化配置需要秘密占位/官方引用时仍只携带引用。
- 迁移 preparation/auth_compat/service_config 的声明性数据，通用行为保留或抽成共享机制。删除已替代的品牌分支和重复数据；删除模块本身不作为成功标准，原有行为回归必须通过。

### 3.5 协议依据与升级条件

已核对：[官方认证规范](https://agentclientprotocol.com/protocol/v1/authentication)、[Terminal Authentication RFD](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/rfds/auth-methods.mdx)。RFD 记录 terminal 于 2026-08-20 稳定，env_var 类型已于 2026-07-27 移除；不再等待该类型发布，也不把 Farfold 的官方环境交付包装为协议 auth method。

先验证当前锁定库的能力、解码和调用；只有确认缺少所需官方能力或存在相关缺陷时才升级，目标稳定依赖须发布 ≥7 天，并完成锁文件及受影响回归。不为统一 Agent 目录批量升级外部 CLI。向外部项目提出改进先准备可审阅复现材料，取得具体对外发布授权后再提交。

### 5.2 单条目工序与并行边界

查官方文档/源码 → 核实发行与启动配置 → 在允许安装范围内连接并保存脱敏声明 → 确定实际路线/所需条件 → 必要时补配方 → 实测安装/认证/模型/首发/续接及失败出口 → 安装版验证 → 填覆盖表。

按真实机制和现成条件分批，不按“大厂一定是某登录类型”预分类。各条目资料与配方研究可并行；共用机制改动统一归口，正式安装替换与候选验收串行，认证涉及共享账号/Keychain 时避免并行变更。任何文件改动前核对现有工作区，禁止覆盖其他执行者的修改。

只 initialize 的探测仍会启动外部程序，npx/uvx 可能下载、执行安装脚本或写缓存，Agent 自身也可能写配置/历史。调查先静态核对，执行前说明具体副作用；复用正常用户环境，不伪称全批只读，不建立私有 HOME。没有账号可以验证安装、连接和登录入口，但首发/续接保持条件缺失未测。

每批对全部宣称已完成的条目执行对应安装版路径；抽样只用于早期发现问题，不能替代其他条目的出口。目录外 Agent 采用同一工序；无官方可用接入面时记录证据和边界，不另建专属工作台或执行循环。

## 6. 阶段三：生命周期、数据迁移与既有旅程回归

## 8. 风险、外部条件与停止规则

- 方法声明、登录成功、订阅、额度及模型实际可用互不替代。缺账号/新秘密授权/干净环境时明确缺什么，保留未测；不能退出日常账号或造私有 HOME 伪装干净环境。
- 官方协议与目录可能变化，配方须有范围与核对日期；缺省/未知数据保持诚实路径，不能按品牌猜命令。
- 只有自然语言登录说明时，查明官方交互并允许用户显式配置；不认定只能等外部 PR 才能使用，也不擅自执行猜测命令。
- 已核实外部缺陷、无法满足的官方依赖和不可用接入面保留失败/不支持证据；Farfold 提供可恢复入口，不承诺解决所有外部版本不兼容。
- 安装、网页登录和真实请求均有副作用；用户操作、账号与密钥的授权范围各自保持。对外 issue/PR、CLI 升级和破坏性管理先形成具体可审阅动作，按具体授权执行。
- 如果某项修复要求第二执行循环、模型代理、改外部 Agent、私有 HOME、用户配置写入或降低产品契约，停止该路径并报告实际冲突；其他符合边界的工作继续。
- LifeModel 真实采集/注入、编辑器、多窗口及其他契约外功能仍不纳入本次接入交付。
